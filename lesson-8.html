Lesson Introduction

Understand how pipeline stages and registers improve datapath timing and throughput.

As datapaths become more complex, a large amount of combinational logic may exist between two registers. A long combinational path can limit the maximum operating frequency.

Pipelining solves this problem by dividing the combinational logic into smaller stages separated by registers.

In this lesson, we'll learn how pipeline stages work, how latency and throughput differ, how pipeline timing is analyzed and how to implement a basic pipeline using Verilog RTL.

Learning Objectives

By the end of this lesson, you should be able to:

Explain what pipelining is and why it is used in digital hardware design.

📊 Analyze Performance

⏱ Timing Analysis

Identify critical paths and understand how pipeline registers divide combinational delays.

💻 Write Pipeline RTL

Implement basic pipelined datapaths using synthesizable Verilog.

1. What is Pipelining?

Understanding the fundamental idea behind pipeline architecture.

Definition

Pipelining is a technique used to divide a large combinational operation into multiple smaller stages separated by registers.

Instead of performing the entire operation in one long clock cycle, the work is divided across multiple stages.

Without Pipelining 


Register
   |
   v
+------+    +------+    +------+    +------+
| Logic| -> | Logic| -> | Logic| -> | Logic|
+------+    +------+    +------+    +------+
                                      |
                                      v
                                   Register

All of the combinational logic lies between the two registers. This can create a long critical path.

With Pipelining 


Register
   |
   v
+------+      +------+
| Logic| ---> | Reg  |
+------+      +------+
                 |
                 v
              +------+
              | Logic|
              +------+
                 |
                 v
              +------+
              | Reg  |
              +------+
                 |
                 v
              +------+
              | Logic|
              +------+
                 |
                 v
              Register

Pipeline registers divide the long combinational path into smaller sections.

Simple Example

Suppose a datapath contains three major operations: 


Operation 1 → Operation 2 → Operation 3

Without pipelining, all three operations may need to complete within one clock cycle. With pipelining, they can be divided into three stages: 


Stage 1 → Register → Stage 2 → Register → Stage 3

Why Use Pipelining?

  • Reduce the amount of combinational logic per clock cycle.
  • Allow a shorter clock period.
  • Increase the potential operating frequency.
  • Improve throughput for repeated operations.

Key Idea

Pipelining divides a long datapath into smaller stages using registers, allowing multiple operations to be processed simultaneously at different stages.

2. Why Do We Need Pipelining?

Understanding why long combinational paths can limit RTL performance.

The Problem with Long Combinational Paths

In a synchronous RTL design, data typically travels from one register through combinational logic and is captured by another register on the next clock edge. 


Source Register
      |
      v
+-------------+
| Combinational|
|    Logic     |
+-------------+
      |
      v
Destination Register

If the combinational logic becomes very large, the data may take too long to reach the destination register. This limits how fast the clock can operate.

Example of a Long Datapath 


Register
   |
   v
  MUX
   |
   v
  ALU
   |
   v
 Comparator
   |
   v
 Shifter
   |
   v
Register

All of these operations may create a long combinational delay if they are placed between the same two registers.

Effect on Clock Frequency

The clock period must be long enough for the slowest register-to-register path to complete. A simplified relationship is: 


Clock Period ≥
Clock-to-Q Delay
+
Combinational Logic Delay
+
Setup Time

Therefore, reducing the combinational delay between registers can allow the design to operate at a higher frequency.

How Pipelining Helps

Pipelining inserts registers between sections of combinational logic. Instead of one long path: 


Register
   |
   v
MUX → ALU → Comparator → Shifter
   |
   v
Register

we can divide the logic into multiple stages: 


Register
   |
   v
MUX → ALU
   |
   v
Pipeline Register
   |
   v
Comparator → Shifter
   |
   v
Pipeline Register

Each stage now performs less combinational work during one clock cycle.

Higher Frequency

If the longest combinational delay is reduced, the clock period can potentially become shorter. For example: 


Without Pipeline:
10 ns combinational delay
Maximum frequency ≈ 100 MHz
With Pipeline:
5 ns per stage
Maximum frequency ≈ 200 MHz

This is a simplified example. Real designs also include register delays, setup time, clock uncertainty and other timing effects.

Pipelining Improves Throughput

Pipelining is particularly useful when many operations must be processed continuously. Multiple pieces of data can occupy different pipeline stages at the same time. 


Cycle 1:
Data A → Stage 1
Cycle 2:
Data A → Stage 2
Data B → Stage 1
Cycle 3:
Data A → Stage 3
Data B → Stage 2
Data C → Stage 1

After the pipeline becomes full, multiple results can be produced at regular clock intervals.

Important Trade-Off

Pipelining does not necessarily make one individual operation finish in fewer stages. Instead, it can improve the rate at which completed operations are produced. This distinction leads to two important concepts:

  • Latency — how long one operation takes to travel through the pipeline.
  • Throughput — how frequently completed operations can be produced.

Key Idea

Pipelining divides long combinational paths into smaller stages so that the design can potentially operate at a higher clock frequency and process a continuous stream of operations with higher throughput.

3. Pipeline Stages

Understanding how a large operation is divided into smaller processing stages.

What is a Pipeline Stage?

A pipeline stage is a portion of a larger operation that performs a specific amount of combinational work. Pipeline stages are separated by registers. 


Stage 1
   |
Register
   |
Stage 2
   |
Register
   |
Stage 3
   |
Register

Basic Three-Stage Pipeline

Consider a datapath that performs three major operations: 


Operation A → Operation B → Operation C

Instead of performing all three operations in one cycle, we can divide them into three pipeline stages. 


        Stage 1          Stage 2          Stage 3
Input ──> Logic A ──> Reg ──> Logic B ──> Reg ──> Logic C ──> Reg

Pipeline Registers

The registers between stages are called pipeline registers. They capture the intermediate result at the active clock edge and hold it while the next stage processes it. 


        Stage 1
           |
           v
     +-----------+
     | Pipeline  |
     | Register  |
     +-----------+
           |
           v
        Stage 2
           |
           v
     +-----------+
     | Pipeline  |
     | Register  |
     +-----------+
           |
           v
        Stage 3

Why Divide the Design into Stages?

  • Reduce combinational delay per stage.
  • Improve the achievable clock frequency.
  • Allow multiple data items to be processed simultaneously.
  • Make large datapaths easier to organize.

Example: Arithmetic Pipeline

Suppose an operation contains: 


Addition → Multiplication → Comparison

A simple pipeline could be: 


Stage 1          Stage 2             Stage 3
Addition         Multiplication      Comparison
   |                  |                  |
   v                  v                  v
 [Reg]              [Reg]              [Reg]

Each register stores the intermediate result before passing it to the next stage.

Pipeline Processing

Once the pipeline is full, different input data items can occupy different stages at the same time. 


Cycle 1:
Data A → Stage 1
Cycle 2:
Data A → Stage 2
Data B → Stage 1
Cycle 3:
Data A → Stage 3
Data B → Stage 2
Data C → Stage 1
Cycle 4:
Data A → Output
Data B → Stage 3
Data C → Stage 2
Data D → Stage 1

This overlapping of operations is the main reason pipelining can increase throughput.

Balanced Pipeline Stages

Ideally, the amount of combinational delay in each pipeline stage should be reasonably balanced. For example: 


Stage 1 → 3 ns
Stage 2 → 3 ns
Stage 3 → 3 ns

is generally more efficient than: 


Stage 1 → 1 ns
Stage 2 → 7 ns
Stage 3 → 1 ns

The longest stage can still limit the clock period. Therefore, pipeline design often involves balancing the work between stages.

Key Idea

A pipeline divides a datapath into stages separated by registers. Each stage performs part of the overall computation, allowing different data items to be processed simultaneously.

4. Pipeline Registers

Understanding how registers separate pipeline stages and store intermediate results.

What is a Pipeline Register?

A pipeline register is a sequential storage element placed between two pipeline stages. It captures the output of one stage at a clock edge and provides that value as the input to the next stage. 


        Stage 1
           |

    +--------------+
    |   Pipeline   |
    |   Register   |
    +--------------+
           |
           v
        Stage 2

Pipeline registers divide a long combinational path into smaller timing paths. Without pipeline registers:

   |

   |
   v
Logic C → Logic D
   |

What Does a Pipeline Register Store?

A pipeline register can store intermediate values required by the next stage. For example: 


Stage 1:
A + B
       ↓
Pipeline Register
       ↓
Stage 2:
Stored Result × C

The register holds the result of the first operation until the next pipeline stage processes it.

Basic Verilog Example 


reg [7:0] stage1_data;
always @(posedge clk) begin
    if (reset)
        stage1_data <= 8'b0;
    else
        stage1_data <= data_in;
end

Here, stage1_data acts as a pipeline register. It captures data_in on the active clock edge.

Pipeline Register Between Two Operations 


always @(*) begin
    stage1_result = data_a + data_b;
end
always @(posedge clk) begin
    if (reset)
        stage2_data <= 8'b0;
    else
        stage2_data <= stage1_result;
end

The combinational logic calculates the intermediate result, and the pipeline register captures it at the clock edge.

Next Pipeline Register

Each pipeline register creates a boundary between clock cycles. This allows different stages to work on different data items simultaneously.

Important Design Consideration

Pipeline registers are sequential elements, so they introduce latency. However, they can also allow the clock frequency to increase by reducing the amount of combinational logic in each stage.

Key Idea

Pipeline registers divide the datapath into clocked stages by storing intermediate results between combinational logic blocks.

They are essential for controlling pipeline timing and enabling overlapped processing.

5. Latency vs Throughput

Understanding the two most important performance concepts in a pipeline.

What is Latency?

Latency is the amount of time or number of clock cycles required for one input to travel through the pipeline and produce its corresponding output.

For a simple three-stage pipeline: 


Input
  |
  v
Stage 1
  |
  v
Stage 2
  |
  v
Stage 3
  |
  v
Output

The first result becomes available after the input has passed through all three stages. If each stage takes one clock cycle, the pipeline has a latency of approximately three clock cycles.

What is Throughput?

Throughput describes how frequently completed results can be produced once the pipeline is operating continuously.

For example, after a three-stage pipeline becomes full: 


Cycle 1:
A → Stage 1
Cycle 2:
A → Stage 2
B → Stage 1
Cycle 3:
A → Stage 3
B → Stage 2
C → Stage 1
Cycle 4:
A → Output
B → Stage 3
C → Stage 2
D → Stage 1
Cycle 5:
B → Output
C → Stage 3
D → Stage 2
E → Stage 1

After the pipeline is full, one completed result can be produced every clock cycle in this ideal example.

Latency vs Throughput

Latency Throughput
Time for one operation to travel through the pipeline. Rate at which completed operations are produced.
Measured in time or clock cycles. Often expressed as results per cycle or results per second.
Pipeline stages contribute to latency. Clock frequency and pipeline utilization affect throughput.

Important Example

Suppose a pipeline has four stages and each stage takes one clock cycle. 


Pipeline Stages = 4
Latency ≈ 4 clock cycles

After the pipeline is full, if a new input enters every cycle, an ideal pipeline can produce: 


1 result per clock cycle

So increasing the number of pipeline stages can increase latency while still allowing high throughput.

Why This Matters in RTL Design

When designing a pipeline, engineers must consider both latency and throughput. A design may require:

  • Low latency for fast response.
  • High throughput for processing large amounts of data.
  • Or a balance between the two depending on the application.

Pipeline Performance

          |                   |

      operation            per cycle

Key Idea

Latency tells us how long one operation takes to travel through the pipeline, while throughput tells us how frequently completed results can be produced.

A pipeline can have higher latency while still providing excellent throughput.

Stage Delay

The combinational logic inside a pipeline stage contributes to the timing delay of that stage. For example: 


Stage 1 = 3 ns
Stage 2 = 4 ns
Stage 3 = 2 ns

The slowest stage is 4 ns. Therefore, before considering clock-to-Q delay, setup time, clock uncertainty and other timing effects, the combinational portion of the pipeline must accommodate the 4 ns stage.

Balanced Pipeline

Ideally, the combinational work should be distributed reasonably evenly between stages. For example: 


Stage 1 → 3 ns
Stage 2 → 3 ns
Stage 3 → 3 ns

This is generally better balanced than: 


Stage 1 → 1 ns
Stage 2 → 7 ns
Stage 3 → 2 ns

In the second example, the 7 ns stage becomes the limiting stage.

Unbalanced Pipeline

Adding pipeline registers does not automatically guarantee a faster design. If one stage contains significantly more combinational logic than the others, that stage can become the critical path.

7. Basic 2-Stage Pipeline

Build a simple two-stage pipeline and understand how data moves between stages.

What is a 2-Stage Pipeline?

A two-stage pipeline divides a computation into two sections of combinational logic separated by a pipeline register. 


             Stage 1              Stage 2
Input ──> Logic A ──> Register ──> Logic B ──> Register ──> Output

Example

Consider the following operation: 


Result = (A + B) + C

We can divide it into two stages. 


Stage 1:
A + B
       ↓
Pipeline Register
       ↓
Stage 2:
(A + B) + C
       ↓
Output Register

Data Flow 


A ──┐
    ├──> ADD ──> Stage 1 Register ──┐
B ──┘                               |
                                    v
                                   ADD ──> Output Register
                                    ^
                                    |
                                    C

The first addition is completed in Stage 1. The intermediate result is stored in the pipeline register. During the next clock cycle, Stage 2 uses that stored value together with C.

Cycle-by-Cycle Operation 


Cycle 1:
A + B
  |
  v
Stage 1 Register
Cycle 2:
Stage 1 Register + C
  |
  v
Output Register

Why Is This Better Than One Long Stage?

Without pipelining, both additions may be placed in one long combinational path: 


A + B + C
      ↓
One long combinational path
      ↓
Register

With pipelining: 


A + B
  |
  v
Register
  |
  v
+ C
  |
  v
Register

The logic is divided across two clock cycles.

Basic Verilog RTL 


module pipeline_2_stage (
    input wire clk,
    input wire reset,
    input wire [7:0] a,
    input wire [7:0] b,
    input wire [7:0] c,
    output reg [7:0] result
);
reg [7:0] stage1;
always @(posedge clk) begin
    if (reset) begin
        stage1 <= 8'b0;
        result <= 8'b0;
    end
    else begin
        // Stage 1
        stage1 <= a + b;
        // Stage 2
        result <= stage1 + c;
    end
end
endmodule

Important Observation

Both assignments occur on the same clock edge, but because nonblocking assignments are used, the second stage uses the previous value of stage1. That is what creates the pipeline behavior. 


At Clock N:
stage1  ← A + B
result  ← previous stage1 + C
At Clock N+1:
stage1  ← new A + B
result  ← previous stage1 + C

Pipeline Latency

For this example, an input requires two pipeline stages before its result appears at the output. Therefore, the pipeline has approximately: 


Latency = 2 clock cycles

Once the pipeline is full, new input data can be accepted every clock cycle.

Key Idea

A 2-stage pipeline divides a computation into two clocked stages. The intermediate result is stored in a pipeline register, allowing new input data to enter the pipeline while previous data continues through the next stage.

Basic Verilog Example 


module pipeline_3_stage (
    input wire clk,
    input wire reset,
    input wire [7:0] a,
    input wire [7:0] b,
    input wire [7:0] c,
    input wire [7:0] d,
    output reg [7:0] result
);
reg [7:0] stage1;
reg [7:0] stage2;
always @(posedge clk) begin
    if (reset) begin
        stage1 <= 8'b0;
        stage2 <= 8'b0;
        result <= 8'b0;
    end
    else begin
        // Stage 1
        stage1 <= a + b;
        // Stage 2
        stage2 <= stage1 * c;
        // Stage 3
        result <= stage2 - d;
    end
end
endmodule

Important Observation

The nonblocking assignments ensure that each stage receives the value from the previous clock cycle. Therefore, the stages operate concurrently on different data items. 


Clock N:
stage1 ← current A + B
stage2 ← previous stage1 × C
result ← previous stage2 - D

Latency

Because the operation passes through three pipeline stages, the latency is approximately: 


Latency = 3 clock cycles

However, once the pipeline is full, a new result can ideally be produced every clock cycle.

Throughput 


Cycle 1 → Input A
Cycle 2 → Input B
Cycle 3 → Input C
Cycle 4 → Input D
After the pipeline fills:
One result per clock cycle

Stage Balancing

The three stages should ideally contain reasonably balanced amounts of combinational logic. For example: 


Stage 1 → 2 ns
Stage 2 → 3 ns
Stage 3 → 2 ns

The second stage is the slowest stage and may therefore influence the maximum clock frequency.

Key Idea

A 3-stage pipeline divides a computation into three clocked stages. Pipeline registers store intermediate results, allowing all stages to work simultaneously on different data items.

The pipeline can have multiple-cycle latency while still achieving high throughput once it is full.

9. Pipeline Timing Diagram

Learn how data moves through pipeline stages across clock cycles.

Why Use a Timing Diagram?

A pipeline timing diagram shows which stage is processing each data item during each clock cycle. It makes the concepts of latency, overlap and throughput easier to understand.

Three-Stage Pipeline

Consider a pipeline containing three stages: 


Stage 1 → Stage 2 → Stage 3

Suppose inputs A, B and C enter the pipeline on consecutive clock cycles.

Timing Table

Clock Cycle Stage 1 Stage 2 Stage 3
1 Data A — —
2 Data B Data A —

4 Data D Data C Data B

Visual Representation 


             Clock Cycle
             1      2      3      4      5
Stage 1      A      B      C      D      E
Stage 2             A      B      C      D

Output                            A      B

Understanding the Diagram

During Cycle 1, Data A enters Stage 1. During Cycle 2, Data A moves to Stage 2 while Data B enters Stage 1. During Cycle 3, Data A reaches Stage 3 while Data B and Data C occupy the earlier stages.

This means that multiple pieces of data are being processed at the same time.

Pipeline Fill

At the beginning, the pipeline is empty. It takes several clock cycles to fill all the stages. For a three-stage pipeline: 


Cycle 1 → Stage 1 active
Cycle 2 → Stages 1 and 2 active
Cycle 3 → Stages 1, 2 and 3 active

After the pipeline becomes full, each additional input can advance through the stages every clock cycle.

For this simplified three-stage example, the first input reaches the output after approximately three clock cycles.

Once the pipeline is full, a new result can ideally be produced every clock cycle.

This is the major performance advantage of pipelining for continuous data processing.

Increasing the number of pipeline stages generally increases the number of cycles required for one input to reach the output. However, it can also reduce the amount of combinational logic per stage and therefore allow a shorter clock period.

A simplified pipeline timing relationship is: 


Clock Period ≥
Clock-to-Q Delay
+
Maximum Combinational Delay
+
Setup Time
+
Timing Margin

The maximum combinational delay is determined by the slowest pipeline stage.

Example

Suppose:

  • Clock-to-Q delay = 1 ns
  • Maximum stage delay = 5 ns
  • Setup time = 1 ns
  • Timing margin = 1 ns

Then a simplified minimum clock period is: 


Clock Period
= 1 ns + 5 ns + 1 ns + 1 ns
= 8 ns

The theoretical maximum frequency is approximately: 


Frequency = 1 / Clock Period
          = 1 / 8 ns
          ≈ 125 MHz

Real timing analysis also considers factors such as clock skew, jitter, uncertainty, routing delay and library timing characteristics.

Balancing Pipeline Stages

One way to improve pipeline performance is to distribute the combinational logic more evenly between stages. 


Before:
Stage 1 → 2 ns
Stage 2 → 5 ns
Stage 3 → 3 ns
After Balancing:
Stage 1 → 3 ns
Stage 2 → 3 ns
Stage 3 → 3 ns

The slowest stage has been reduced from 5 ns to 3 ns. This can potentially allow a shorter clock period.

Adding Another Pipeline Stage

Another approach is to divide a long stage into smaller stages. For example: 


Before:
Register
   |
   v
Logic A → Logic B
   |
   v
Register

can become: 


Register
   |
   v
Logic A
   |
   v
Pipeline Register
   |
   v
Logic B
   |
   v
Register

This can reduce the combinational delay per clock cycle, but it also adds another pipeline stage and therefore increases latency.

Performance Trade-Off

Change Possible Benefit Possible Cost
Add Pipeline Stage Shorter combinational path Higher latency
Balance Stages Better clock frequency May require redesign
Reduce Logic Lower stage delay Can require architectural changes

Critical Path in RTL Design

When designing RTL, engineers should identify logic paths that may become timing bottlenecks. Typical examples include:

  • Large arithmetic operations.
  • Deep multiplexer chains.
  • Long combinational logic chains.
  • Large comparison logic.
  • Unbalanced pipeline stages.

Key Idea

The slowest pipeline stage can determine the minimum clock period. Good pipeline design attempts to balance the combinational delay between stages while considering the trade-off between frequency, latency and hardware cost.

11. Pipeline RTL Implementation

Implementing a basic multi-stage pipeline using synthesizable Verilog RTL.

Pipeline RTL Structure

A pipelined RTL design typically contains combinational logic followed by registers at the boundaries of each stage. For a simple three-stage pipeline: 


Input
  |
  v
Combinational Logic
  |
  v
Pipeline Register 1
  |
  v
Combinational Logic
  |
  v
Pipeline Register 2
  |
  v
Combinational Logic
  |
  v
Output Register

Example Design

Let's implement a simple three-stage arithmetic pipeline. The operation will be: 


Stage 1:
A + B
Stage 2:
Stage 1 Result × C
Stage 3:
Stage 2 Result - D

Complete Verilog RTL 


module pipeline_3_stage (
    input wire clk,
    input wire reset,
    input wire [7:0] a,
    input wire [7:0] b,
    input wire [7:0] c,
    input wire [7:0] d,
    output reg [7:0] result
);
reg [7:0] stage1;
reg [7:0] stage2;
// =====================================
// Pipeline Stages
// =====================================
always @(posedge clk) begin
    if (reset) begin
        stage1 <= 8'b0;
        stage2 <= 8'b0;
        result <= 8'b0;
    end
    else begin
        // Stage 1
        stage1 <= a + b;
        // Stage 2
        stage2 <= stage1 * c;
        // Stage 3
        result <= stage2 - d;
    end
end
endmodule

Understanding the RTL

The design uses three sequential pipeline stages. At every rising edge of the clock: 


stage1 <= a + b;
stage2 <= stage1 * c;
result <= stage2 - d;

Because these are nonblocking assignments, all three assignments use the values that existed before the clock edge. This is what allows the pipeline stages to operate concurrently.

Example

Suppose: 


A = 2
B = 3
C = 4
D = 5

The mathematical result is: 


((A + B) × C) - D
= ((2 + 3) × 4) - 5
= 20 - 5
= 15

The pipeline does not perform the entire calculation in one clock cycle. Instead: 


Stage 1:
2 + 3 = 5
Stage 2:
5 × 4 = 20
Stage 3:
20 - 5 = 15

Cycle-by-Cycle View 


Clock 1:
stage1 = A + B
Clock 2:
stage1 = new A + B
stage2 = previous stage1 × C
Clock 3:
stage1 = new A + B
stage2 = previous stage1 × C
result = previous stage2 - D

This demonstrates how different input transactions can occupy different pipeline stages at the same time.

Important RTL Rule

Use Nonblocking Assignments for Sequential Logic

Pipeline registers are sequential logic. Therefore, clocked RTL should normally use <= nonblocking assignments. 


always @(posedge clk) begin
    stage1 <= a + b;
    stage2 <= stage1 * c;
    result <= stage2 - d;
end

Using nonblocking assignments models the simultaneous state updates that occur at a clock edge.

Reset Behavior

The reset condition clears every pipeline register. This is important because otherwise the pipeline can initially contain unknown values. 


if (reset) begin
    stage1 <= 8'b0;
    stage2 <= 8'b0;
    result <= 8'b0;
end

Key Observation

A pipeline is fundamentally a combination of: 


Combinational Logic
        +
Pipeline Registers
        +
Clock

The registers establish the stage boundaries, while the combinational logic performs the work within each stage.

Key Idea

Pipelined RTL divides a computation into clocked stages. Nonblocking assignments allow each pipeline register to capture the previous stage's result while the other stages process different data during the same clock cycle.

13. Pipeline Hazards — Introduction

Understand why pipelines can encounter situations that prevent normal data flow.

What is a Pipeline Hazard?

A pipeline hazard is a condition that prevents a pipeline from proceeding normally in the expected sequence. Hazards become important when one operation depends on another operation, when hardware resources are shared, or when the normal control flow changes.

In a simple independent-data pipeline, every input can move forward one stage per clock cycle. However, real designs can introduce situations where the next operation cannot safely proceed.

Simple Example

Consider two operations: 


Operation A
    |
    v
Produces Data X
Operation B
    |
    v
Needs Data X

If Operation B reaches a pipeline stage before Data X is available, the pipeline must somehow handle that dependency.

Why Hazards Occur

Pipeline hazards can occur for several reasons. Common categories include:

Hazard Type Basic Idea
Data Hazard One operation depends on data produced by another operation.
Structural Hazard Two operations require the same hardware resource at the same time.
Control Hazard Changing control flow makes the next operation uncertain.

1. Data Hazard

A data hazard occurs when one operation needs a value that is being produced by another operation. For example: 


Instruction A:
R1 = R2 + R3
Instruction B:
R4 = R1 + R5

Instruction B needs the value of R1 produced by Instruction A. In a pipeline, the two operations may overlap, creating a dependency problem.

2. Structural Hazard

A structural hazard occurs when multiple pipeline operations require the same hardware resource at the same time. For example, if two stages require a single shared memory interface, both operations cannot use it simultaneously. 


Stage 1 ──┐
          |
          v
       Shared
       Resource
          ^
          |
Stage 2 ──┘

3. Control Hazard

A control hazard occurs when the next operation depends on a control decision. Branches are a common example. 


        Branch
          |
       +--+--+
       |     |
      Path A Path B

Until the branch decision is known, the pipeline may not know which instruction or operation should enter the following stages.

How Can Hazards Be Handled?

Depending on the architecture, different techniques can be used. Examples include:

  • Pipeline stalls
  • Forwarding or bypassing
  • Resource duplication
  • Pipeline flushing
  • Hazard detection logic

These techniques are especially important in processor pipelines. We will focus first on understanding the underlying dependency concepts before studying advanced hazard handling.

Pipeline Stall

A stall temporarily prevents a pipeline stage from advancing. An empty slot created in the pipeline is often called a bubble. 


Normal:
Cycle 1 → A
Cycle 2 → B
Cycle 3 → C
With Stall:
Cycle 1 → A
Cycle 2 → B
Cycle 3 → Bubble
Cycle 4 → C

A stall can reduce throughput, but it may be necessary to preserve correct operation.

Hazards in Basic RTL Pipelines

Even a simple RTL datapath can encounter dependencies. For example: 


Stage 1 → produces result X
Stage 2 → requires result X

The designer must determine whether the value is available at the required time. This is why pipeline timing and data dependencies must be considered together during RTL design.

Important Distinction

Pipeline hazards are not automatically bugs. A hazard is a condition that requires the architecture or control logic to take appropriate action. The actual design must ensure that the final behavior remains correct.

Key Idea

Pipeline hazards are situations that can prevent normal pipeline progress. The major categories are data hazards, structural hazards and control hazards.

Understanding dependencies is the first step toward designing correct and efficient pipelined systems.

14. Data Dependencies

Understand how one operation can depend on the result of another operation.

What is a Data Dependency?

A data dependency occurs when one operation requires a value that is produced or modified by another operation. In a pipeline, these dependencies are important because multiple operations execute at overlapping times.

Simple Example

Consider two operations: 


Operation 1:
X = A + B
Operation 2:
Y = X + C

Operation 2 requires the value of X produced by Operation 1. Therefore: 


Operation 1
     |
     | Produces X
     v
Operation 2
     |
     | Uses X
     v
Result

Why Is This Important in a Pipeline?

Suppose the two operations are placed into consecutive pipeline stages: 


Stage 1:
X = A + B
      |
      v
Pipeline Register
      |
      v
Stage 2:
Y = X + C

This is straightforward because the pipeline register stores the result of Stage 1 before Stage 2 uses it.

Dependency Across Pipeline Cycles

Consider the following simplified timing: 


Cycle 1:
Stage 1 → Calculate X
Cycle 2:
Stage 2 → Use X

The register between the stages ensures that Stage 2 receives the value produced by Stage 1.

Read-After-Write Dependency

One common dependency is a Read-After-Write (RAW) dependency. It occurs when a later operation reads a value that an earlier operation writes. 


Instruction A:
R1 = R2 + R3
Instruction B:
R4 = R1 + R5

Instruction B reads R1, but Instruction A must first produce the new value of R1. Therefore: 


Instruction A
     |
     | Writes R1
     v
Instruction B
     |
     | Reads R1
     v
Result

Pipeline Timing Example

Cycle Stage 1 Stage 2 Stage 3
1 Instruction A — —
2 Instruction B Instruction A —
3 Instruction C Instruction B Instruction A

If Instruction B needs a value that Instruction A has not yet made available, additional mechanisms may be required.

Dependency Handling

Common techniques for handling pipeline data dependencies include:

  • Forwarding: Send a newly generated value directly to the stage that needs it.
  • Stalling: Temporarily stop the pipeline until the required data becomes available.
  • Scheduling: Reorder independent operations when the architecture allows it.

Forwarding Concept

Forwarding, also called bypassing, allows a result to be sent directly from one pipeline stage to another without waiting for it to be written back and read again through the normal path. 


             +----------------+
             |                |
             v                |
Stage 1 → Stage 2 → Stage 3

| ^
| :--- |

   +------ Forwarding -------+

Forwarding can reduce unnecessary pipeline stalls when the required value is already available somewhere inside the pipeline.

Stall Example

If the required value is not yet available, the pipeline may need to wait. 


Cycle 1 → Instruction A
Cycle 2 → Instruction B
Cycle 3 → STALL
Cycle 4 → Instruction B continues

The stall introduces a bubble into the pipeline.

Important Design Question

Think About It

If Stage 2 requires a value produced by Stage 1, but Stage 1 has not yet produced the value at the required time, what should the design do?

  • Forward the value if it is available.
  • Otherwise, stall the pipeline.

Data Dependencies in RTL

At the RTL level, pipeline registers naturally introduce clock-cycle boundaries. For example: 


always @(posedge clk) begin
    stage1 <= a + b;
    stage2 <= stage1 + c;
end

Here, stage2 receives the previous value of stage1 because nonblocking assignments update the registers together at the clock edge.

Key Idea

Data dependencies occur when one operation needs data produced by another operation. In pipelined systems, dependencies must be handled carefully using techniques such as forwarding or stalling when necessary.

15. Pipeline Design Considerations

Important factors to consider when designing a practical RTL pipeline.

1. Stage Balancing

Pipeline stages should contain reasonably balanced amounts of combinational logic. If one stage is significantly slower than the others, it can limit the maximum clock frequency. 


Poorly Balanced:
Stage 1 → 2 ns
Stage 2 → 8 ns
Stage 3 → 2 ns
Better Balanced:
Stage 1 → 4 ns
Stage 2 → 4 ns
Stage 3 → 4 ns

2. Latency

Adding pipeline stages generally increases the number of clock cycles required for one input to reach the output. 


2-stage pipeline → approximately 2 cycles
4-stage pipeline → approximately 4 cycles

The correct number of pipeline stages depends on the system requirements.

3. Throughput

A pipeline should ideally accept new data at the required rate. Once the pipeline is full, a well-designed pipeline can produce one result per clock cycle for a continuous stream of independent data. 


Input:
A → B → C → D → E
Output:
A → B → C → D → E
One result can be produced per cycle
after the pipeline is full.

4. Pipeline Register Overhead

Pipeline registers are not free. They introduce clock-to-Q delay, setup requirements, clock power and additional hardware. Therefore, adding more registers does not always produce a better design. 


More Pipeline Stages
        |
        +----> Smaller Logic Per Stage
        |
        +----> Potentially Higher Frequency
        |
        +----> Higher Latency
        |
        +----> More Registers
        |
        +----> More Clock Power

5. Reset Strategy

Pipeline registers may need to be initialized or invalidated during reset. For a simple design, reset can clear the pipeline registers. 


if (reset) begin
    stage1 <= 8'b0;
    stage2 <= 8'b0;
    result <= 8'b0;
end

In larger designs, valid bits are often used so that reset or empty pipeline stages are not interpreted as valid data.

6. Valid Signal

When a pipeline can contain empty stages, a valid signal can indicate whether the data in a stage represents a real transaction. 


Data  +  Valid
  |
  v
Pipeline Stage
valid = 1
Data represents a valid transaction.
valid = 0
Data is not valid.

7. Data Alignment

When multiple pieces of information belong to the same transaction, they must remain aligned as they move through the pipeline. For example, data, address, control information and valid information may all need to advance through matching pipeline stages. 


Data
  ↓
Stage 1 → Stage 2 → Stage 3
Address
  ↓
Stage 1 → Stage 2 → Stage 3
Control
  ↓
Stage 1 → Stage 2 → Stage 3
Valid
  ↓
Stage 1 → Stage 2 → Stage 3

If one signal is delayed by an extra cycle while another is not, the transaction can become corrupted.

8. Pipeline Hazards

Dependencies between operations can require additional control logic. Depending on the architecture, hazards may be handled using:

  • Forwarding
  • Stalling
  • Bubble insertion
  • Resource management
  • Control logic

The previous section introduced pipeline hazards and data dependencies. In practical designs, the chosen hazard-handling technique depends on the architecture and required performance.

9. Area and Power

Adding pipeline registers increases hardware resources and clock activity. Therefore, pipeline optimization is usually a trade-off between performance, area, power and latency. 


Performance
     ↕
Area
     ↕
Power
     ↕
Latency

10. Verification Complexity

A pipelined design can be more difficult to verify because an input does not necessarily produce an output immediately. The testbench must account for the pipeline latency. 


Input A
   |
   |
   |  Pipeline Latency
   |
   v
Output A

A useful verification strategy is to maintain expected results and compare them with the actual output after the appropriate pipeline delay.

11. Clock Frequency

The desired operating frequency is one of the major factors when deciding how deeply to pipeline a design. A simplified relationship is: 


Higher Frequency
       ↓
Shorter Clock Period
       ↓
Smaller Combinational Delay Per Stage
       ↓
Potentially More Pipeline Stages

However, increasing the number of stages also introduces additional register overhead and latency.

12. Do Not Over-Pipeline

Adding pipeline stages simply to increase the stage count is not always beneficial. Excessive pipelining can increase:

  • Latency
  • Register count
  • Clock power
  • Control complexity
  • Verification complexity

The goal is to find an appropriate balance for the application.

Practical Design Example

Suppose a datapath contains the following combinational delays: 


Logic A → 2 ns
Logic B → 6 ns
Logic C → 2 ns

Without careful partitioning, Logic B may become the timing bottleneck. A designer could consider restructuring the datapath so that the work is distributed more evenly. 


Before:
Stage 1 → 2 ns
Stage 2 → 6 ns
Stage 3 → 2 ns
Possible balanced design:
Stage 1 → 3 ns
Stage 2 → 3 ns
Stage 3 → 4 ns

The exact solution depends on the logic and architecture. The goal is to avoid unnecessarily large differences between stage delays.

Pipeline Design Checklist

  • Is the combinational logic reasonably balanced?
  • Does the pipeline meet the required clock frequency?
  • Is the latency acceptable?
  • Is the required throughput achieved?
  • Are data and control signals aligned?
  • Are pipeline hazards handled correctly?
  • Is reset behavior clearly defined?
  • Are valid signals required?
  • Are area and power acceptable?
  • Can the pipeline be verified effectively?

Key Idea

Good pipeline design is a balance between frequency, latency, throughput, area, power, control complexity and verification effort.

The fastest pipeline is not necessarily the best pipeline. The architecture must meet the requirements of the complete system.

Key Performance Trade-Off 


More Pipeline Stages
        |
        +----> Potentially Higher Frequency

The goal of pipeline design is not simply to maximize the number of stages. The goal is to achieve the required combination of frequency, throughput, latency, area, power and correctness.

Final Takeaway

A pipeline allows different portions of a computation to operate concurrently on different data transactions.

Understanding pipeline stages, registers, timing, latency, throughput, data dependencies and hazards is fundamental to designing high-performance RTL and SoC datapaths.

Key Takeaways

The most important concepts to remember from this lesson.

  • Pipelining divides a large computation into smaller stages.
  • Pipeline registers separate consecutive stages.
  • Combinational logic performs the work inside each stage.
  • Latency is the time required for a transaction to pass through the pipeline.
  • Throughput is the rate at which completed results are produced.
  • Multiple transactions can be processed simultaneously in different pipeline stages.
  • The slowest stage can determine the maximum operating frequency.
  • Data dependencies can create pipeline hazards.
  • Forwarding and stalling are common techniques for handling dependencies.
  • Valid signals can identify meaningful transactions.
  • Pipeline RTL normally uses nonblocking assignments in clocked logic.
  • Waveform analysis is important for verifying cycle-by-cycle pipeline behavior.

Remember

A good pipeline balances frequency, throughput, latency, area, power and design complexity.
