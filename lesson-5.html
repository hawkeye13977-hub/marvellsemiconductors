What is a Procedural Block?

Understanding how Verilog describes procedural hardware behavior.

A procedural block is a section of Verilog code containing statements that execute when a specified event occurs.

The most commonly used procedural construct for RTL design is the always block.

Basic Structure 

always @(sensitivity_list) begin

    // RTL statements

end

The sensitivity information determines when the procedural block is triggered.

The always Block

The fundamental procedural construct used in Verilog RTL.

The always block repeatedly executes whenever its specified triggering event occurs.

Combinational Example 

always @(*) begin

    y = a & b;

end

Sequential Example 

always @(posedge clk) begin

    q <= d;

end
Type Typical Block Purpose
Combinational always @(*) Logic based on current inputs
Sequential always @(posedge clk) Clocked state storage

Blocking Assignment (=)

Understanding how blocking assignments execute inside procedural blocks.

A blocking assignment uses the = operator. The assignment updates the left-hand side immediately within the procedural flow of the block.

Basic Syntax 

always @(*) begin

    y = a & b;

end

Example 

always @(*) begin

    x = a;
    y = x;

end

The statements execute in order. First: x = a is executed. Then: y = x uses the updated value of x.

Important Concept

Blocking assignments execute sequentially inside the procedural block. The next statement sees the value assigned by the previous statement.

Where is Blocking Assignment Commonly Used?

  • Combinational logic.
  • Temporary variables inside combinational calculations.
  • Procedural calculations where statement ordering matters.

RTL Rule

For combinational logic written using always @(*), blocking assignment = is commonly used.

Non-Blocking Assignment (<=)

Understanding the assignment style commonly used for sequential RTL.

A non-blocking assignment uses the <= operator. It is commonly used to describe clocked sequential logic such as flip-flops, registers and counters.

Basic Syntax 

always @(posedge clk) begin

    q <= d;

end

Example 

always @(posedge clk) begin

    q1 <= d1;
    q2 <= q1;

end

At the clock edge, the right-hand-side values are evaluated using the current state, and the updates are scheduled for the non-blocking assignment update region.

Therefore, in the example above, q2 receives the previous value of q1, rather than the value assigned to q1 during the same clock event.

Where is Non-Blocking Assignment Used?

  • Flip-flops.
  • Registers.
  • Counters.
  • Finite State Machines.
  • Other clocked sequential logic.

RTL Rule

For clocked sequential logic, use non-blocking assignment (<=) to model state updates.

Why Does This Matter?

Consider a two-stage register pipeline: 

always @(posedge clk) begin

    stage1 <= data;
    stage2 <= stage1;

end

The first stage captures the current value of data. The second stage captures the previous value of stage1. This models how two flip-flops connected in sequence behave in hardware.

Key Idea

Non-blocking assignment allows multiple sequential elements to update as if they respond to the same clock edge.

Blocking (=) vs Non-Blocking (<=)

Understanding the most important Verilog assignment rule for RTL design.

Blocking Assignment (=)

  • Uses the = operator.
  • Statements execute in procedural order.
  • The next statement sees the updated value.
  • Commonly used for combinational logic.
always @(*) begin

    a = b;
    c = a;

end

Here, c sees the value assigned to a by the previous statement.

Non-Blocking Assignment (<=)

  • Uses the <= operator.
  • Updates are scheduled rather than immediately visible to following statements.
  • Models simultaneous state updates at a clock edge.
  • Commonly used for sequential logic.
always @(posedge clk) begin

    a <= b;
    c <= a;

end

Here, c receives the previous value of a.

Quick Comparison

Feature Blocking (=) Non-Blocking (<=)
Operator = <=
Execution behavior Procedural order Updates are scheduled
Common RTL usage Combinational logic Sequential logic
Typical block always @(*) always @(posedge clk)
Typical hardware Combinational logic Flip-flops / registers

Important Example 

always @(posedge clk) begin

    q1 <= d;
    q2 <= q1;

end

Suppose before the clock edge: 

q1 = 0
q2 = 0
d  = 1

At the rising edge: 

q1 <= 1
q2 <= 0

After the update: 

q1 = 1
q2 = 0

On the next clock edge, q2 can capture the new value of q1. This behavior represents a simple two-stage pipeline.

RTL Golden Rule

Combinational logic → Blocking (=)

Sequential logic → Non-Blocking (<=)

Combinational Coding Style

Learn how to correctly describe combinational logic using an always block.

Combinational logic can be described using always @(*). The output should depend only on the current values of the inputs.

Example: 2:1 Multiplexer 

module mux2to1(

    input a,
    input b,
    input sel,

    output reg y

);

always @(*) begin

    if (sel)
        y = b;
    else
        y = a;

end

endmodule

How It Works

  • When sel = 0, output y = a.
  • When sel = 1, output y = b.
  • The block executes whenever an input used by the logic changes.
  • The blocking assignment = is used for this combinational logic.

Important Rule: Assign Every Output

In a combinational always @(*) block, every output should receive a value for every possible input condition.

For example, this is a correct implementation: 

always @(*) begin

    if (sel)
        y = b;
    else
        y = a;

end

Both possible values of sel assign a value to y.

Why Is This Important?

If an output is not assigned in some condition, the synthesizer may infer a latch because the hardware must retain the previous value.

Another Useful Coding Style

For more complex combinational logic, a default assignment can be used before conditional statements. 

always @(*) begin

    y = 1'b0;

    if (sel)
        y = b;
    else
        y = a;

end

The default assignment ensures that y always has a defined value.

Combinational RTL Checklist

  • Use always @(*) for combinational procedural logic.
  • Use blocking assignment =.
  • Assign every output for every possible condition.
  • Avoid unintended latches.
  • Keep the logic dependent only on current inputs.

Sequential Coding Style

Learn how to describe clocked sequential logic correctly in Verilog.

Sequential logic contains storage elements such as flip-flops and registers. In Verilog, clocked sequential logic is commonly described using an always @(posedge clk) block.

Basic Sequential RTL Pattern 

always @(posedge clk) begin

    q <= d;

end

The block executes when the clock has a rising edge. At that point, the input value is captured into the register.

Example: D Flip-Flop 

module d_flip_flop (

    input clk,
    input d,

    output reg q

);

always @(posedge clk) begin

    q <= d;

end

endmodule

Example: Register with Reset 

module register_4bit (

    input        clk,
    input        reset,
    input  [3:0] d,
    output reg [3:0] q

);

always @(posedge clk) begin

    if (reset)
        q <= 4'b0000;
    else
        q <= d;

end

endmodule

How It Works

  1. The circuit waits for the rising edge of clk.
  2. When the rising edge occurs, the procedural block executes.
  3. If reset = 1, the register is cleared.
  4. If reset = 0, the input data is captured.
  5. The stored value remains unchanged until the next active clock edge.

Why Use <=?

For clocked sequential RTL, use the non-blocking assignment (<=). It models the behavior of multiple flip-flops updating in response to the same clock edge.

Sequential RTL Checklist

  • Use always @(posedge clk) for positive-edge-triggered sequential logic.
  • Use <= for state updates.
  • Use reset according to the design specification.
  • Make sure every stored signal has a clearly defined update behavior.
  • Do not use blocking assignments for normal clocked state updates.

Remember

Combinational RTL

always @(*) + =

Sequential RTL

always @(posedge clk) + <=

Practical Example: Two-Stage Pipeline

See how blocking and non-blocking assignments produce different RTL behavior.

Two-Stage Pipeline

Consider two registers connected in sequence: 


        ┌─────────┐       ┌─────────┐
D ────→ │ Stage 1 │ ────→ │ Stage 2 │ ────→ Q
        └─────────┘       └─────────┘
             ↑                 ↑
             └────── CLK ──────┘

Each stage represents a flip-flop. Both stages receive the same clock.

Correct Sequential RTL 

always @(posedge clk) begin

    stage1 <= data;
    stage2 <= stage1;

end

Initial Values 


data   = 1
stage1 = 0
stage2 = 0

At the first rising clock edge: 


stage1 <= data;     // stage1 gets 1
stage2 <= stage1;   // stage2 gets previous stage1 = 0

After the clock edge: 


stage1 = 1
stage2 = 0

At the next rising edge, assuming data is still 1: 


stage1 = 1
stage2 = 1

Pipeline Behavior

Clock Edge Data Stage 1 Stage 2
Initial 1 0 0
↑ 1 1 1 0
↑ 2 1 1 1

Why Non-Blocking Assignment?

The two registers are hardware elements that respond to the same clock edge. Using <= allows both state updates to be based on the values that existed before the clock event.

Important Interview Point

If blocking assignments were used for ordinary clocked state updates: 

always @(posedge clk) begin

    stage1 = data;
    stage2 = stage1;

end

stage2 could immediately see the new value assigned to stage1 during procedural execution. That does not model the intended two-flip-flop pipeline behavior.

Therefore, for normal sequential RTL, non-blocking assignment (<=) is the standard coding style.

Common RTL Coding Mistakes

Avoid these common mistakes when writing combinational and sequential RTL.

1. Using Blocking Assignment for Sequential Logic

A common beginner mistake is using = for normal clocked state updates. 

// Avoid for normal sequential state

always @(posedge clk) begin

    q = d;

end

The preferred coding style is: 

always @(posedge clk) begin

    q <= d;

end

2. Using Non-Blocking Assignment for Simple Combinational Logic

For combinational procedural logic, blocking assignment is normally the clearer coding style. 

always @(*) begin

    y = a & b;

end

Use = for this type of combinational calculation.

3. Incomplete Assignment in Combinational Logic

If an output is not assigned under every possible condition, synthesis may infer a latch.

Example of potentially unintended latch inference: 

always @(*) begin

    if (sel)
        y = a;

end

When sel = 0, there is no assignment to y. The circuit therefore needs to retain the previous value of y, which can result in latch inference.

A complete version is: 

always @(*) begin

    if (sel)
        y = a;
    else
        y = b;

end

4. Forgetting the Clock in Sequential Logic

Clocked sequential logic must be triggered by the appropriate clock event. 

always @(posedge clk) begin

    q <= d;

end

The posedge clk indicates that the register updates on the rising edge of the clock.

5. Accidentally Creating Multiple Drivers

A signal should normally have a clear and controlled driving source. Avoid assigning the same RTL signal from multiple procedural blocks unless the design intentionally requires that structure and the target technology supports it. 

always @(posedge clk)
    q <= a;

always @(posedge clk)
    q <= b;

This creates multiple procedural drivers for q and is generally not the intended RTL structure.

RTL Checklist

  • Combinational logic → always @(*) + =.
  • Sequential logic → always @(posedge clk) + <=.
  • Assign combinational outputs for all possible conditions.
  • Use the correct clock and reset sensitivity.
  • Avoid unintended multiple drivers.
  • Keep RTL simple, predictable and synthesizable.

Combinational vs Sequential always Blocks

Learn how to choose the correct always block for your RTL design.

Combinational RTL 

always @(*) begin

    y = a & b;

end
  • Triggered when relevant inputs change.
  • No clock is required.
  • Output depends on current inputs.
  • Blocking assignment = is commonly used.
  • All outputs should be assigned for every possible condition.

Sequential RTL 

always @(posedge clk) begin

    q <= d;

end
  • Triggered by the specified clock edge.
  • Uses a clock for synchronous state updates.
  • Stores previous state.
  • Non-blocking assignment <= is commonly used.
  • Models flip-flops and registers.

Quick Comparison

Feature Combinational Sequential
Typical block always @(*) always @(posedge clk)
Clock Not required Required for synchronous logic
Memory No Yes
Assignment = <=
Typical hardware Logic gates / MUX Flip-flops / registers
State No stored state Stores state

Example: Combining Both Styles

A typical RTL design may contain both combinational and sequential logic. For example, consider a register that increments its value: 

always @(*) begin

    next_count = count + 1'b1;

end


always @(posedge clk) begin

    count <= next_count;

end

The first block calculates the next value using combinational logic. The second block stores that value in the register at the clock edge.

Simple Mental Model

Combinational logic

"What should the next value be?"

Sequential logic

"When should the value be stored?"

Latch Inference

Understand how incomplete combinational RTL can unintentionally create storage.

What is a Latch?

A latch is a storage element whose output can retain its previous value when the required input condition is not active.

When writing combinational RTL, we normally do not want the synthesis tool to create a latch accidentally.

Example of Incomplete Combinational Logic 

always @(*) begin

    if (enable)
        y = a;

end

The problem is that there is no assignment to y when enable = 0. The hardware therefore needs to retain the previous value of y. This can cause the synthesis tool to infer a latch.

Corrected Version 

always @(*) begin

    if (enable)
        y = a;
    else
        y = 1'b0;

end

Now y receives a value for both possible values of enable.

Another Safe Coding Style

A default assignment can be placed at the beginning of the block. 

always @(*) begin

    y = 1'b0;

    if (enable)
        y = a;

end

If enable = 0, the default value is used. If enable = 1, the value of a replaces the default value.

How to Avoid Unintended Latches

  • Assign every combinational output on every possible path.
  • Use if/else when all conditions need explicit behavior.
  • Use default assignments when appropriate.
  • Review synthesis warnings for inferred latches.
  • Use simulation to verify all input conditions.

Interview Example

An interviewer may show you this code: 

always @(*) begin

    if (sel)
        y = a;

end

and ask: “What hardware can this code infer?”

The important answer is: Because y is not assigned when sel = 0, synthesis may infer a latch to preserve the previous value of y.

Conditional Statements in Verilog

Using if, else if and else to describe hardware decisions.

Conditional statements allow RTL code to select different hardware behavior based on input conditions. The most common conditional construct is: if / else if / else.

Basic Syntax 

if (condition) begin

    // statements

end
else begin

    // statements

end

Example: 2:1 MUX 

always @(*) begin

    if (sel)
        y = b;
    else
        y = a;

end

When sel = 1, the output is assigned b. When sel = 0, the output is assigned a.

if / else if / else

Multiple conditions can be checked using else if. 

always @(*) begin

    if (sel == 2'b00)
        y = a;
    else if (sel == 2'b01)
        y = b;
    else if (sel == 2'b10)
        y = c;
    else
        y = d;

end

This structure can describe a selection between four possible inputs.

Important RTL Rule

For combinational logic, make sure every possible condition assigns a value to the output. 

always @(*) begin

    if (sel == 2'b00)
        y = a;
    else if (sel == 2'b01)
        y = b;
    else if (sel == 2'b10)
        y = c;
    else
        y = d;

end

The final else handles the remaining condition, so y is assigned for every possible 2-bit value of sel.

Nested Conditions

Conditions can also be placed inside other conditions. 

always @(*) begin

    if (enable) begin

        if (sel)
            y = b;
        else
            y = a;

    end
    else begin

        y = 1'b0;

    end

end

Although nested conditions are valid, keep RTL simple and readable. Complex decision logic can sometimes be expressed more clearly using case statements, which we will cover later.

Common Uses

  • Multiplexers.
  • Priority logic.
  • Enable logic.
  • Control logic.
  • Combinational decision-making.
  • Conditional register updates in sequential logic.

Remember

if checks the first condition, else if checks additional conditions, and else handles the remaining case.

case Statement

Use case statements to describe multiple selection conditions clearly.

The case statement is another procedural construct used to select one behavior from multiple possible conditions. It is especially useful when a signal can have several possible values.

Basic Syntax 

always @(*) begin

    case (select)

        value1: statement1;
        value2: statement2;
        value3: statement3;

        default: statement_default;

    endcase

end

Example: 4:1 Multiplexer 

module mux4to1 (

    input  [1:0] sel,
    input        a,
    input        b,
    input        c,
    input        d,

    output reg   y

);

always @(*) begin

    case (sel)

        2'b00: y = a;
        2'b01: y = b;
        2'b10: y = c;
        2'b11: y = d;

        default: y = 1'b0;

    endcase

end

endmodule

How It Works

SEL Output
00 A
01 B
10 C
11 D

The case expression is evaluated and compared with each case item. The matching item determines which assignment is executed.

Why Use default?

A default case handles values that do not match any explicit case item. It is a good RTL practice to make the intended behavior explicit. 

default:
    y = 1'b0;

case vs if / else

Feature if / else case
Best suited for Conditional decisions Multiple discrete values
Example Enable conditions Opcode / MUX selection
Readability Good for few conditions Often clearer for many values

Example: Decoder 

always @(*) begin

    case (sel)

        2'b00: y = 4'b0001;
        2'b01: y = 4'b0010;
        2'b10: y = 4'b0100;
        2'b11: y = 4'b1000;

        default: y = 4'b0000;

    endcase

end

Here, the case statement can describe a simple 2-to-4 decoder.

RTL Rule

For combinational case statements, ensure that the output has a defined value for all relevant conditions. A default branch is often useful for making the intended behavior explicit.

Where case Statements Are Commonly Used

  • Multiplexers.
  • Decoders.
  • Opcode decoding.
  • Control logic.
  • Finite State Machines.
  • Protocol and command decoding.

casez and casex

Understanding wildcard matching in Verilog case statements.

Verilog provides casez and casex statements for situations where some bits of a value are treated as wildcards during comparison. These constructs are useful when designing decoders, instruction decoders and control logic.

1. casez

casez treats Z values and ? bits as don't-care positions during matching. The ? symbol is commonly used to indicate a bit that does not matter for the comparison.

Example 
always @(*) begin

    casez (opcode)

        4'b10??: result = 1'b1;
        4'b01??: result = 1'b0;

        default: result = 1'b0;

    endcase

end

For the pattern: 

4'b10??

the first two bits must be 10, while the last two bits can have any value. For example:

Opcode Matches 10???
1000 Yes
1001 Yes
1010 Yes
1011 Yes
1100 No

2. casex

casex treats both X and Z values as don't-care bits during comparison. Example: 

always @(*) begin

    casex (opcode)

        4'b10xx: result = 1'b1;
        4'b01xx: result = 1'b0;

        default: result = 1'b0;

    endcase

end

The x positions are treated as wildcards.

case vs casez vs casex

Statement Wildcard Behavior Typical Use
case Exact 4-state comparison Normal decoding
casez Z / ? can be don't-care Wildcard decoding
casex X / Z can be don't-care Generally avoided in RTL

Why is casex Usually Avoided?

In simulation, an X often represents an unknown value. Using casex can cause an unknown signal to match a wildcard pattern, potentially hiding an initialization or design problem. For example, if an input unexpectedly becomes: 

4'b1x10

a casex statement may treat the unknown X as a don't-care value. That can make simulation appear correct even though the design contains an unknown condition.

RTL Best Practice

When wildcard matching is required, casez with ? is generally preferred over casex because it does not automatically treat X values as don't-care.

Practical Example: Opcode Decoder 

always @(*) begin

    casez (opcode)

        8'b1010_????:
            instruction = 4'b0001;

        8'b1100_????:
            instruction = 4'b0010;

        8'b1110_????:
            instruction = 4'b0011;

        default:
            instruction = 4'b0000;

    endcase

end

Here, the upper four bits identify the instruction group while the lower four bits are ignored.

Interview Tip

A common interview question is: What is the difference between case, casez and casex?

  • case performs normal 4-state matching.
  • casez allows Z and ? wildcard matching.
  • casex treats X and Z as don't-care values.
  • casex can hide unknown-state problems and is therefore generally avoided in synthesizable RTL.

Remember

case → exact matching
casez → wildcard matching
casex → X/Z wildcard matching — use with caution

for Loop in Verilog

Using loops to describe repetitive hardware operations.

The for loop is commonly used in Verilog to repeat a set of statements a specific number of times. It is especially useful when describing repetitive operations such as array processing, bit manipulation and hardware structures.

Basic Syntax 

for (initialization; condition; increment) begin

    // statements

end

For example: 

integer i;

always @(*) begin

    for (i = 0; i < 4; i = i + 1) begin

        // statements

    end

end

Understanding the Three Parts

Part Example Purpose
Initialization i = 0 Sets the starting value
Condition i < 4 Determines whether the loop continues
Increment i = i + 1 Changes the loop variable

Simple Example

Suppose we want to invert every bit of a 4-bit input. Without a loop: 

always @(*) begin

    y[0] = ~a[0];
    y[1] = ~a[1];
    y[2] = ~a[2];
    y[3] = ~a[3];

end

A for loop can describe the same operation more compactly: 

integer i;

always @(*) begin

    for (i = 0; i < 4; i = i + 1) begin

        y[i] = ~a[i];

    end

end

Here the loop processes bits: 

i = 0 → y[0] = ~a[0]

i = 1 → y[1] = ~a[1]

i = 2 → y[2] = ~a[2]

i = 3 → y[3] = ~a[3]

Important RTL Concept

A synthesizable for loop does not normally mean that hardware executes the loop sequentially like software. During synthesis, the loop is typically unrolled into the corresponding hardware structure.

Practical Example: 4-bit Bit Inverter 

module bit_inverter (

    input  [3:0] a,
    output reg [3:0] y

);

integer i;

always @(*) begin

    for (i = 0; i < 4; i = i + 1) begin

        y[i] = ~a[i];

    end

end

endmodule

How It Works

  • a is a 4-bit input.
  • y is a 4-bit output.
  • The loop iterates from 0 through 3.
  • Each input bit is inverted.
  • All four output bits are assigned.

Another Common Use: Checking Bits

A loop can also be used to examine each bit of a vector. For example, we can determine whether any bit of a 4-bit input is set to 1: 

module any_bit_set (

    input  [3:0] a,
    output reg   y

);

integer i;

always @(*) begin

    y = 1'b0;

    for (i = 0; i < 4; i = i + 1) begin

        if (a[i])
            y = 1'b1;

    end

end

endmodule

The output becomes 1 if at least one bit of a is 1. For example:

A Y
0000 0
0001 1
0100 1
1000 1
1111 1

Common Mistakes

  • Forgetting to initialize the loop variable.
  • Using an incorrect loop termination condition.
  • Creating an infinite loop by never changing the loop variable.
  • Failing to assign outputs in all required paths inside a combinational block.
  • Assuming a synthesizable loop automatically creates sequential software-like execution.

Interview Tip

Be prepared to explain that a synthesizable for loop is generally elaborated/unrolled by synthesis to create the required hardware rather than creating a software-style runtime loop.

Key Syntax to Remember 

for (i = 0; i < WIDTH; i = i + 1) begin

    // RTL statements

end

Remember

Initialize → Check → Execute → Increment → Repeat

while Loop in Verilog

Understanding conditional loops and where they are commonly used in Verilog.

The while loop repeatedly executes a group of statements as long as a specified condition remains true. Unlike a for loop, a while loop does not automatically provide initialization and increment expressions. The loop continues based entirely on its condition.

Basic Syntax 

while (condition) begin

    // statements

end

Simple Example 

integer i;

initial begin

    i = 0;

    while (i < 4) begin

        i = i + 1;

    end

end

The loop executes while i < 4. The sequence is: 

i = 0
 ↓
i < 4 → Yes
 ↓
i = 1
 ↓
i < 4 → Yes
 ↓
i = 2
 ↓
i < 4 → Yes
 ↓
i = 3
 ↓
i < 4 → Yes
 ↓
i = 4
 ↓
i < 4 → No
 ↓
Loop ends

Important Concept

The condition is checked before each iteration. If the condition is false initially, the loop body does not execute even once.

for vs while

Feature for Loop while Loop
Initialization Usually included in loop syntax Usually written separately
Condition Specified in loop syntax Specified in loop syntax
Increment Usually included in loop syntax Must be handled explicitly
Best suited for Known/fixed iterations Condition-based repetition

Testbench Example

The while loop is particularly useful in testbenches when an operation needs to continue until a condition becomes true. 

integer count;

initial begin

    count = 0;

    while (count < 5) begin

        #10;

        count = count + 1;

    end

end

Here, the testbench waits for five iterations, with a 10 time-unit delay between iterations.

Important Difference: RTL vs Testbench

A while loop can be used in RTL, but the loop must have a clearly synthesizable and bounded behavior for synthesis tools. In testbenches, while loops are much more flexible and are commonly used for stimulus generation and simulation control.

Example: Waiting for a Condition 

while (!done) begin

    @(posedge clk);

end

This waits for clock edges until done becomes 1. This style is commonly useful in verification testbenches.

Common Mistake: Infinite Loop

A while loop can become an infinite loop if the condition never becomes false. For example: 

integer i;

initial begin

    i = 0;

    while (i < 4) begin

        // i is never changed

    end

end

Here, i remains 0 forever, so i < 4 always remains true. The loop never terminates.

How to Avoid Infinite Loops

  • Make sure the loop condition can eventually become false.
  • Update the variable controlling the condition.
  • For testbench loops, make sure simulation time can advance when required.

Interview Question

What is the difference between a for loop and a while loop?

A for loop is generally convenient when the number of iterations is known or follows a predictable range. A while loop is controlled primarily by a condition and is useful when repetition depends on whether that condition remains true.

Remember

Check condition → Execute → Update condition → Repeat
