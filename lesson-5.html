Verilog Procedural Blocks and Coding Styles

Learn how procedural blocks describe sequential and combinational RTL behavior.

A procedural block is a section of Verilog code containing statements that execute in a defined procedural context.

Procedural blocks are commonly used to describe the behavior of combinational logic and sequential logic.

In this lesson, you will learn how to use always blocks, assignments, conditional statements, loops, arrays, memories, parameters and generate constructs to write RTL code.

What is a Procedural Block?

Understanding how Verilog describes procedural hardware behavior.

A procedural block is a section of Verilog code containing statements that execute when a specified event occurs.

The most commonly used procedural construct for RTL design is the always block.

Basic Structure 

always @(sensitivity_list) begin

    // RTL statements

end

The sensitivity information determines when the procedural block is triggered.

The always Block

The fundamental procedural construct used in Verilog RTL.

The always block repeatedly executes whenever its specified triggering event occurs.

Combinational Example 

always @(*) begin

    y = a & b;

end

This describes combinational behavior based on the current input signals.

Sequential Example 

always @(posedge clk) begin

    q <= d;

end

This describes clocked sequential behavior where the value of d is captured on the rising edge of clk.

Common always Block Types

Type Typical Block Purpose
Combinational always @(*) Logic based on current inputs
Sequential always @(posedge clk) Clocked state storage

Key Idea

always @(*) → combinational behavior
always @(posedge clk) → clocked sequential behavior

Sensitivity Lists

Understanding when an always block is triggered.

A sensitivity list specifies the signals or events that cause an always block to execute.

When a signal in the sensitivity list changes, the procedural block is triggered.

Explicit Sensitivity List 

always @(a or b) begin

    y = a & b;

end

Here, the block is triggered whenever a or b changes.

Combinational Sensitivity List

For combinational logic, always @(*) is commonly used. 

always @(*) begin

    y = a & b;

end

The * tells the simulator to automatically include the signals referenced by the procedural block.

Why is always @(*) Useful?

Consider a combinational block containing several input signals: 

always @(*) begin

    if (sel)
        y = a & b;
    else
        y = c | d;

end

Using always @(*) avoids manually listing every signal used by the block.

Sequential Sensitivity List

Clocked sequential logic can use an edge in the sensitivity list. For example: 

always @(posedge clk) begin

    q <= d;

end

The block executes when clk changes from 0 → 1.

Negative-Edge Triggering

A sequential block can also respond to the falling edge of a clock. 

always @(negedge clk) begin

    q <= d;

end

Here, the block executes when the clock changes from 1 → 0.

Sensitivity List Comparison

Construct Triggered When Typical Use
always @(a or b) a or b changes Combinational logic
always @(*) Referenced input changes Combinational logic
always @(posedge clk) Clock rising edge Positive-edge sequential logic
always @(negedge clk) Clock falling edge Negative-edge sequential logic

RTL Rule

For combinational procedural logic, use always @(*) so that changes to the signals referenced by the block trigger its execution.

Negative-Edge Sequential Logic

Sequential logic can also update on the falling edge of the clock.

A sequential block can be triggered by either the rising edge or falling edge of a clock. The falling edge is represented using negedge.

Example 

always @(negedge clk) begin

    q <= d;

end

Here, the register captures d when the clock changes from: 

1 → 0

posedge vs negedge

Trigger Clock Transition
posedge clk 0 → 1
negedge clk 1 → 0

Key Point

posedge and negedge both describe edge-triggered sequential behavior; the difference is which clock transition triggers the update.

Asynchronous Reset

Understanding how a reset can affect sequential logic independently of the clock.

An asynchronous reset can change the state of a sequential element without waiting for a clock edge. The reset signal is therefore included in the sensitivity list.

Example 

always @(posedge clk or posedge reset) begin

    if (reset)
        q <= 1'b0;
    else
        q <= d;

end

How It Works

  1. If reset becomes active, q is cleared without waiting for the clock.
  2. When reset is inactive, the circuit waits for the rising edge of clk.
  3. At the rising edge, d is captured into q.

Synchronous vs Asynchronous Reset

Feature Synchronous Reset Asynchronous Reset
Reset in sensitivity list No Yes
Waits for clock edge Yes No
Example always @(posedge clk) always @(posedge clk or posedge reset)

Key Point

Synchronous reset is evaluated at the clock edge, while asynchronous reset can take effect independently of the clock.

Two-Stage Pipeline

Understanding how sequential stages transfer data from one register to the next.

A pipeline divides a data path into multiple sequential stages. Each stage is separated by a register. A simple two-stage pipeline can be described using two registers: 

always @(posedge clk) begin

    stage1 <= data;
    stage2 <= stage1;

end

How It Works

At every rising edge of the clock: 


data
  ↓
stage1
  ↓
stage2

The first stage captures the current input data, while the second stage captures the previous value of stage1.

Example

Clock Edge Data Stage 1 Stage 2
Initial 1010 0000 0000
↑ 1 1010 1010 0000
↑ 2 0101 0101 1010
↑ 3 1111 1111 0101

Why Non-Blocking Assignment Matters

Both assignments use the non-blocking assignment operator: 

stage1 <= data;
stage2 <= stage1;

The assignments are evaluated using the values that existed before the clocked update. Therefore, stage2 receives the old value of stage1, while stage1 receives the current value of data.

Pipeline Behavior 


Clock 1:
Data → Stage 1

Clock 2:
Data → Stage 1
Stage 1(previous) → Stage 2

Clock 3:
Data → Stage 1
Stage 1(previous) → Stage 2

Key Idea

Each pipeline stage stores data for one clock cycle before passing it to the next stage.

This is one of the important reasons non-blocking assignments are used for clocked sequential RTL.

Blocking vs Non-Blocking Simulation

Observe how blocking and non-blocking assignments behave in sequential RTL.

    input clk,

    q_blocking = d;

end

endmodule

With a single independent register assignment, the difference may not be obvious from the final waveform. The difference becomes much more important when multiple sequential assignments interact. For example: 

always @(posedge clk) begin

    stage1 <= data;
    stage2 <= stage1;

end

With non-blocking assignments, stage2 receives the previous value of stage1, which correctly models two sequential pipeline stages.

RTL Rule

For clocked sequential RTL, use non-blocking assignments (<=) to model register state updates.

Blocking Assignment (=)

Understanding how blocking assignments execute inside procedural blocks.

A blocking assignment uses the = operator. The assignment executes immediately, and the next statement in the procedural block waits until the assignment has completed.

Basic Example 

always @(*) begin

    a = b;
    c = a;

end

Here, a receives the value of b before the next statement executes. Therefore, c receives the updated value of a.

Execution Order 

b
↓
a = b
↓
c = a
↓
End of procedural block

Example 

reg a;
reg b;
reg c;

always @(*) begin

    a = b;
    c = a;

end

Important Concept

Blocking assignments execute in the order in which they appear in the procedural block.

Typical Use

Blocking assignments are commonly associated with combinational procedural logic.

RTL Rule

For combinational logic modeled using a procedural block, = is commonly used for assignments.

Non-Blocking Assignment (<=)

Understanding how non-blocking assignments model clocked sequential behavior.

A non-blocking assignment uses the <= operator. Unlike a blocking assignment, the update does not take effect immediately. The update is scheduled, allowing other statements in the same procedural block to execute before the new value is applied.

Basic Example 

always @(posedge clk) begin

    q <= d;

end

This is a common way to describe a clocked storage element. At the rising edge of clk, the value of d is captured and assigned to q.

Multiple Non-Blocking Assignments 

always @(posedge clk) begin

    a <= b;
    c <= a;

end

Both assignments are evaluated using the values that existed before the clocked update. This makes non-blocking assignments suitable for modeling multiple flip-flops that update together.

Example: Two Registers 

always @(posedge clk) begin

    q1 <= d;
    q2 <= q1;

end

At a clock edge: 

d
↓
q1

q1
↓
q2

The old value of q1 is transferred to q2, while q1 captures the current value of d.

Blocking vs Non-Blocking

Feature Blocking (=) Non-Blocking (<=)
Operator = <=
Update behavior Immediate Scheduled
Execution style Sequential Updates together
Common RTL use Combinational logic Sequential logic

RTL Rule

For clocked sequential logic, use non-blocking assignments (<=).

if / else Statements

Using conditional statements to make decisions in Verilog RTL.

The if statement is used in Verilog procedural blocks to conditionally execute statements. It allows RTL code to make decisions based on signal values.

Basic if Statement 

always @(*) begin

    if (a)
        y = 1'b1;

end

If a = 1, the assignment to y executes. If a = 0, the assignment does not execute.

if / else

The else block executes when the condition is false. 

always @(*) begin

    if (a)
        y = 1'b1;
    else
        y = 1'b0;

end

This describes: 

a = 1 → y = 1
a = 0 → y = 0

This is equivalent to the simple combinational function: 

y = a;

if / else if / else

Multiple conditions can be checked using else if. 

always @(*) begin

    if (a)
        y = 2'b01;
    else if (b)
        y = 2'b10;
    else
        y = 2'b00;

end

The conditions are evaluated from top to bottom. The first true condition determines which assignment executes.

Priority Behavior

When multiple conditions are true, the first true condition in an if / else if chain gets priority. 

if (a)
    y = 1;
else if (b)
    y = 0;

If both a and b are 1, the first condition wins. 

a = 1
b = 1
y = 1

Nested if Statements

An if statement can be placed inside another if statement. 

always @(*) begin

    if (enable) begin

        if (valid)
            y = data;
        else
            y = 0;

    end
    else begin

        y = 0;

    end

end

Here, valid is checked only when enable is active.

if Statement in Sequential Logic

Conditional statements are also commonly used inside clocked always blocks. For example, a register with an enable signal: 

always @(posedge clk) begin

    if (enable)
        q <= d;

end

The register updates only when enable = 1. If enable = 0, no assignment occurs and the register retains its previous value.

if with Reset

One of the most common RTL patterns is reset logic. 

always @(posedge clk) begin

    if (reset)
        q <= 1'b0;
    else
        q <= d;

end

The operation can be understood as: 

Clock edge
    ↓
Check reset
    ↓
reset = 1 ?
   / \
 Yes  No
  ↓    ↓
Q = 0  Q = D

Important RTL Pattern

if (reset) state <= RESET_VALUE; else state <= NEXT_VALUE;

if with Counter

Conditional statements can also control a counter. 

always @(posedge clk) begin

    if (reset)
        count <= 4'b0000;
    else if (enable)
        count <= count + 1'b1;
    else
        count <= count;

end
Reset Enable Operation
1 X Count = 0000
0 1 Count increments
0 0 Count holds

Combinational if and Latch Inference

Understanding why every output should be assigned in combinational logic.

Complete Assignment in Combinational Logic

When using an always @(*) block to describe combinational logic, every output should be assigned for every possible input condition.

Consider this example: 

always @(*) begin

    if (enable)
        y = d;

end

When enable = 1, y receives d. But when enable = 0, there is no assignment to y. The previous value of y must therefore be retained, which can result in latch inference.

Avoiding the Latch

A common solution is to provide an assignment for both conditions. 

always @(*) begin

    if (enable)
        y = d;
    else
        y = 1'b0;

end

Now y receives a value whether enable is 1 or 0.

Default Assignment Technique

Another common coding style is to assign a default value first and then override it when a condition is true. 

always @(*) begin

    y = 1'b0;

    if (enable)
        y = d;

end

This guarantees that y always receives a value during the execution of the combinational block.

Why Latches Can Be a Problem

An unintended latch means that the synthesized hardware contains storage behavior that may not have been intended by the RTL designer. This can make timing, verification and design behavior more difficult to understand.

RTL Rule

For combinational always blocks, make sure every output is assigned for every possible condition.

Quick Comparison

Code Style Result
if (enable) y = d; May infer a latch
if (enable) y = d; else y = 0; Complete combinational assignment
Default assignment + if Complete combinational assignment

case Statement

Using case statements to select between multiple conditions.

The case statement is used when a signal needs to be compared against multiple possible values. It is commonly used to describe decoders, multiplexers and control logic.

Basic Syntax 

always @(*) begin

    case (select)

        2'b00: y = a;
        2'b01: y = b;
        2'b10: y = c;
        2'b11: y = d;

    endcase

end

The expression inside case is compared with each case item. The statement associated with the matching item is executed.

Example: 4-to-1 Multiplexer 

always @(*) begin

    case (sel)

        2'b00: y = a;
        2'b01: y = b;
        2'b10: y = c;
        2'b11: y = d;

    endcase

end
sel Output
00 a
01 b
10 c
11 d

default Case

A default branch can be used when none of the case items match. 

always @(*) begin

    case (sel)

        2'b00: y = a;
        2'b01: y = b;
        2'b10: y = c;
        2'b11: y = d;

        default: y = 1'b0;

    endcase

end

Using a default assignment is useful for making the intended behavior explicit when no listed case item matches.

case vs if

if case
Good for conditions and ranges Good for comparing one expression against multiple values
Can naturally express priority Commonly used for selection logic
Often used for enable/reset conditions Often used for decoders and multiplexers

RTL Tip

When using case in combinational logic, ensure that the output receives an appropriate value for every possible condition.

casez and casex

Using wildcard matching in Verilog case statements.

casez

casez allows certain bits to be treated as don't-care values during matching. The symbol ? can be used as a wildcard.

Example 
always @(*) begin

    casez (opcode)

        4'b1???: y = 1'b1;
        4'b01??: y = 1'b0;
        default: y = 1'b0;

    endcase

end

For example, the pattern: 

4'b1???

matches any 4-bit value whose most significant bit is 1.

casex

casex treats both x and z values as don't-care values during matching. 

always @(*) begin

    casex (opcode)

        4'b1xxx: y = 1'b1;
        4'b01xx: y = 1'b0;
        default: y = 1'b0;

    endcase

end

case vs casez vs casex

Statement Matching Behavior
case Normal exact matching
casez Allows z / ? wildcard matching
casex Treats x and z as don't-care values

Priority in Case Statements

When multiple case items can match, the ordering of the items can matter depending on the case construct and matching patterns. For priority-based decisions, carefully design the patterns and ordering. 

casez (opcode)

    4'b1???: y = 1'b1;
    4'b10??: y = 1'b0;

endcase

The first matching item is selected in a normal procedural case statement.

RTL Caution

Wildcard matching can make a pattern match more values than expected. Use casez and casex carefully and make the intended matching behavior clear.

Verilog Loops

Using loops to repeat procedural statements in Verilog.

Loops allow a group of procedural statements to execute repeatedly. They are especially useful in testbenches and procedural RTL code.

1. for Loop

A for loop is useful when the number of iterations is known or controlled by a loop variable. 

integer i;

for (i = 0; i < 10; i = i + 1) begin

    $display("i = %0d", i);

end

The loop starts with i = 0, continues while i < 10, and increments i after each iteration.

2. while Loop

A while loop continues executing as long as its condition remains true. 

integer i;

i = 0;

while (i < 5) begin

    $display("i = %0d", i);

    i = i + 1;

end

The condition is checked before each iteration.

3. repeat Loop

A repeat loop executes a statement or block a fixed number of times. 

repeat (5) begin

    $display("Hello");

end

The block executes exactly five times.

4. forever Loop

A forever loop repeats continuously until the simulation is terminated or the loop is otherwise exited. 

forever begin

    #5 clk = ~clk;

end

This pattern is commonly used to generate a continuously toggling clock in a testbench.

Clock Generation Example 

initial begin

    clk = 0;

    forever #5 clk = ~clk;

end

Here, the clock starts at 0 and toggles every 5 time units. Therefore, a complete clock period is: 

5 + 5 = 10 time units

Loop Comparison

Loop Main Purpose
for Known number or range of iterations
while Continue while a condition is true
repeat Fixed number of repetitions
forever Continuous repetition

Important Concept

The appropriate loop depends on whether repetition is controlled by a counter, a condition, a fixed number, or continuous execution.

EDA Playground Practice — Counter

Use a loop to generate a clock and observe a counter changing over time.

  1. The clock starts at 0.
  2. The forever loop toggles the clock every 5 time units.
  3. The reset is initially asserted.
  4. After 10 time units, reset is released.
  5. The counter increments on every rising edge of the clock.
  6. The simulation runs for another 100 time units.

  • count[3:0]

What to Observe

  • The clock toggles continuously because of the forever loop.
  • The counter changes only on the rising edge of the clock.
  • Reset forces the counter to zero.
  • The counter increments after reset is released.

Common Mistakes

  • Forgetting to initialize clk.
  • Forgetting to release reset.
  • Using the wrong clock period.
  • Forgetting that forever continues until simulation termination.
  • Confusing the testbench clock-generation loop with the RTL counter logic.

initial Block

Understanding one-time procedural execution in Verilog.

The initial block is a procedural block in Verilog that starts executing at the beginning of simulation. An initial block normally executes its statements once and finishes after reaching the end of the block.

Basic Syntax 

initial begin

    // statements

end

Simple Example 

initial begin

    a = 0;
    b = 1;

end

The statements execute sequentially at the beginning of simulation: 

a = 0
↓
b = 1
↓
initial block completes

Using Delays

An initial block can contain delays to control when stimulus is applied during simulation. 

initial begin

    a = 0;

    #10;
    a = 1;

    #10;
    a = 0;

end

The sequence is:

Simulation Time A
0 0
10 1
20 0

initial vs always

Feature initial always
Starts At beginning of simulation At beginning and repeatedly triggers
Execution Normally executes once Repeats according to its trigger
Common use Testbench stimulus RTL logic / testbench processes
Typical example Driving inputs Clock generation / RTL behavior

Multiple initial Blocks

A Verilog testbench can contain multiple initial blocks. These blocks start at the beginning of simulation and execute concurrently. 

initial begin

    clk = 0;

end

initial begin

    reset = 1;

end

initial begin

    $display("Simulation started");

end

Each initial block performs its own procedural activity independently.

Key Idea

initial → normally executes once from the beginning of simulation

It is especially useful for initializing signals, applying testbench stimulus, displaying results and controlling simulation.

Arrays and Memories

Understanding how Verilog represents collections of bits and storage locations.

Verilog provides arrays to represent groups of bits and collections of storage elements. Arrays are especially useful when modeling registers, memories, buffers and other storage structures.

Packed Arrays

A packed array represents a collection of bits grouped together as a single vector. 

reg [7:0] data;

This represents an 8-bit packed vector. Individual bits can be accessed using an index. 

data[0]
data[1]
data[7]

Unpacked Arrays

An unpacked array represents multiple separate elements. 

reg [7:0] memory [0:15];

This represents a memory containing:

  • 16 memory locations
  • 8 bits per location
  • 128 bits of total storage

Packed vs Unpacked

Declaration Meaning
reg [7:0] data; One 8-bit vector
reg [7:0] memory [0:15]; 16 elements, each 8 bits

What is a Memory?

A memory can be modeled as an array of storage locations. Each location is identified using an address. 

reg [7:0] memory [0:15];

The memory above has:

  • Depth = 16 locations
  • Width = 8 bits per location

Memory Size

Depth × Width

16 × 8 = 128 bits

Memory Addressing

Each memory location can be accessed using its index. For example: 

memory[0]
memory[1]
memory[2]
...
memory[15]

The address selects which storage location is being accessed.

Key Idea

Packed array → collection of bits as a vector
Unpacked array → collection of separate elements
Memory → array of storage locations

Memory Initialization

Initializing memory locations before using stored data.

A memory can be initialized by assigning known values to its storage locations before the memory is used. This is especially useful in simulation and testbench environments.

Initialize All Locations

A for loop can be used to initialize every memory location to the same value. 

integer i;

initial begin

    for (i = 0; i < 16; i = i + 1) begin

        memory[i] = 8'b00000000;

    end

end

For a 16-location memory, the loop initializes: 

memory[0]  = 00000000
memory[1]  = 00000000
memory[2]  = 00000000
...
memory[15] = 00000000

Loading Different Values

Individual memory locations can also be initialized with different values. 

initial begin

    memory[0] = 8'h10;
    memory[1] = 8'h20;
    memory[2] = 8'h30;
    memory[3] = 8'h40;

end

Hexadecimal Representation

Hexadecimal notation is often convenient when working with memory because each hexadecimal digit represents four binary bits.

Hexadecimal Binary
8'h10 00010000
8'h20 00100000
8'h30 00110000
8'h40 01000000

Why Initialize Memory?

  • Provides known values for simulation.
  • Makes testbench behavior easier to understand.
  • Allows predefined data to be available before testing.
  • Helps avoid unexpected unknown values during simulation.

Key Idea

A for loop can initialize an entire memory efficiently, while individual assignments can preload selected memory locations.

Memory Read and Write Operations

Understanding how RTL accesses data stored in memory.

Writing to Memory

A memory location can be written by specifying its address and assigning a value to that location. 

memory[3] = 8'b10101010;

This stores the value 10101010 in memory location 3.

Reading from Memory

The contents of a memory location can be read by accessing its address. 

data = memory[3];

This reads the contents of memory location 3 and assigns the value to data.

Example 

reg [7:0] memory [0:15];
reg [7:0] data;

memory[3] = 8'b10101010;

data = memory[3];

After the write operation: 

memory[3] = 10101010

After the read operation: 

data = 10101010

The address determines which memory location is accessed.

Parameters and localparam

Making Verilog modules reusable and configurable.

What is a Parameter?

A parameter is a constant value that can be used to configure a Verilog module. Parameters are commonly used for widths, sizes and other design configuration values. 

module counter #(

    parameter WIDTH = 8

) (

    input clk,
    input reset,

    output reg [WIDTH-1:0] count

);

Here, WIDTH controls the size of the counter.

  • WIDTH = 8 → 8-bit counter
  • WIDTH = 16 → 16-bit counter

Why Use Parameters?

  • Make RTL reusable.
  • Avoid duplicate modules.
  • Make designs configurable.
  • Support different hardware sizes.
  • Improve scalability.

Parameterized Counter 

module counter #(

    parameter WIDTH = 8

) (

    input clk,
    input reset,

    output reg [WIDTH-1:0] count

);

always @(posedge clk) begin

    if (reset)
        count <= {WIDTH{1'b0}};
    else
        count <= count + 1'b1;

end

endmodule

The expression: 

{WIDTH{1'b0}}

creates a vector containing WIDTH zeros. For example: 

WIDTH = 4
→ 0000

WIDTH = 8
→ 00000000

Parameter Override

A parameter can be overridden when the module is instantiated. 

counter #(

    .WIDTH(4)

) counter_4bit (

    .clk(clk),
    .reset(reset),
    .count(count)

);

Another instance can use a different width: 

counter #(

    .WIDTH(16)

) counter_16bit (

    .clk(clk),
    .reset(reset),
    .count(count)

);

What is localparam?

A localparam is an internal constant. Unlike a regular parameter, it is intended to remain fixed inside the module and cannot be overridden from outside. 

module example #(

    parameter WIDTH = 8

);

localparam MAX_VALUE = (1 << WIDTH) - 1;

endmodule

parameter vs localparam

Feature parameter localparam
Constant value Yes Yes
Configurable Yes No
Can be overridden Yes No
Typical use Module configuration Internal constants

Key Idea

parameter → configurable constant

localparam → internal constant

Generate Blocks

Creating repeated or conditional hardware structures during elaboration.

A generate block is used to create hardware structures repeatedly or conditionally during elaboration.

Instead of manually writing the same hardware multiple times, generate constructs allow the RTL designer to describe the repetition once.

Why Use Generate Blocks?

  • Create repeated hardware automatically.
  • Reduce duplicate RTL code.
  • Make parameterized designs scalable.
  • Create arrays of identical hardware structures.
  • Support configurable hardware architectures.

Generate-for Loop

A generate-for loop uses a genvar to create multiple hardware structures. 

genvar i;

generate

    for (i = 0; i < 4; i = i + 1) begin : gen_block

        // Hardware generated here

    end

endgenerate

What is genvar?

genvar is used as the loop variable for a generate-for construct. If the loop executes four times during elaboration, four hardware structures are generated. 

i = 0 → Hardware 0
i = 1 → Hardware 1
i = 2 → Hardware 2
i = 3 → Hardware 3

Important RTL Concept

A generate loop is not a runtime loop. It is evaluated during elaboration and is used to create hardware structures.

Generate Loop vs Procedural for Loop

Generate Loop Procedural for Loop
Elaboration time Procedural execution
Creates hardware structures Repeats procedural statements
Uses genvar Uses a loop variable
Commonly used for repeated hardware Commonly used inside procedural blocks

Example: Generate Four AND Gates

Instead of manually writing four AND operations: 

assign y[0] = a[0] & b[0];
assign y[1] = a[1] & b[1];
assign y[2] = a[2] & b[2];
assign y[3] = a[3] & b[3];

A generate loop can describe the repeated structure: 

genvar i;

generate

    for (i = 0; i < 4; i = i + 1) begin : gen_and

        assign y[i] = a[i] & b[i];

    end

endgenerate

Parameterized Generate

Generate blocks become especially useful when combined with parameters. 

module and_array #(

    parameter WIDTH = 4

) (

    input [WIDTH-1:0] a,
    input [WIDTH-1:0] b,

    output [WIDTH-1:0] y

);

genvar i;

generate

    for (i = 0; i < WIDTH; i = i + 1) begin : gen_and

        assign y[i] = a[i] & b[i];

    end

endgenerate

endmodule

The same module can therefore generate different hardware sizes.

  • WIDTH = 4 → 4 AND operations
  • WIDTH = 8 → 8 AND operations
  • WIDTH = 32 → 32 AND operations
  • WIDTH = 64 → 64 AND operations

Conditional Generate

Generate constructs can also conditionally create hardware based on a constant expression. 

generate

    if (WIDTH == 8) begin : gen_8bit

        // 8-bit implementation

    end

    else begin : gen_other

        // Other implementation

    end

endgenerate

The condition is evaluated during elaboration.

Key Idea

generate → creates hardware structures

genvar → controls generate-for

parameter + generate → scalable RTL

generate → elaboration time

Parameterized D Flip-Flop Array

Using generate blocks to create multiple identical flip-flops.

Generate blocks can be used to create multiple identical flip-flops. The number of flip-flops can be controlled using a parameter.

RTL Design 

module dff_array #(

    parameter WIDTH = 4

) (

    input clk,
    input reset,

    input [WIDTH-1:0] d,

    output [WIDTH-1:0] q

);

genvar i;

generate

    for (i = 0; i < WIDTH; i = i + 1) begin : gen_dff

        reg q_bit;

        always @(posedge clk) begin

            if (reset)
                q_bit <= 1'b0;
            else
                q_bit <= d[i];

        end

        assign q[i] = q_bit;

    end

endgenerate

endmodule

What Does This Create?

For WIDTH = 4, the generate loop creates four D flip-flop structures. 

d[0] → DFF → q[0]
d[1] → DFF → q[1]
d[2] → DFF → q[2]
d[3] → DFF → q[3]

If WIDTH is changed to 8, the same RTL structure creates eight D flip-flop structures.

Why This Is Useful

  • Avoids manually writing multiple identical flip-flops.
  • Allows the design size to be controlled by a parameter.
  • Makes the RTL reusable.
  • Demonstrates how generate and parameters work together.

Important Concept

Generate creates the repeated hardware structure during elaboration.

The parameter determines how many copies are created.

Generate vs Procedural for Loop

Understanding the difference between hardware generation and procedural execution.

Generate Loop 

genvar i;

generate

    for (i = 0; i < WIDTH; i = i + 1) begin

        assign y[i] = a[i] & b[i];

Procedural for Loop

    for (i = 0; i < WIDTH; i = i + 1) begin

Both constructs can describe synthesizable hardware in appropriate contexts, but they operate at different abstraction mechanisms.

Common Mistakes

Avoid these common problems when writing Verilog procedural RTL.

1. Missing Assignments

In combinational logic, failing to assign an output in every possible condition can result in unintended latch inference. 

always @(*) begin

    if (enable)
        y = d;

end

Prefer complete assignments: 

always @(*) begin

    if (enable)
        y = d;
    else
        y = 0;

end

2. Blocking Assignment in Sequential Logic

Using blocking assignments in clocked sequential logic can produce simulation behavior that does not model the intended register updates.

For clocked sequential RTL, use: 

always @(posedge clk) begin

    q <= d;

end

3. Incorrect Sensitivity List

A combinational procedural block should respond to the signals that affect its output.

Using: 

always @(*)

helps automatically include signals referenced by the block.

4. Incorrect Reset Handling

Make sure the reset style matches the intended design. For example, a synchronous reset uses: 

always @(posedge clk) begin

    if (reset)
        q <= 0;

end

An asynchronous reset includes reset in the sensitivity list.

5. Confusing Generate and Procedural Loops

A generate loop creates hardware structures during elaboration, whereas a procedural loop executes within a procedural block.

Remember: 

generate → hardware structure

procedural for → procedural repetition

6. Forgetting Memory Initialization in Simulation

Uninitialized memory locations can contain unknown values during simulation. Initialize the memory when known starting values are required. 

integer i;

initial begin

    for (i = 0; i < 16; i = i + 1)
        memory[i] = 8'b0;

end

RTL Checklist

  • Use complete assignments for combinational outputs.
  • Use non-blocking assignments for clocked sequential logic.
  • Use appropriate sensitivity information.
  • Follow the required reset architecture.
  • Understand whether a loop is procedural or generate-time.
  • Initialize memory when the simulation requires known values.
