What is a Finite State Machine?

Understanding how digital systems move between defined states.

A Finite State Machine (FSM) is a digital design model used to describe a system that can exist in a finite number of defined states.

The FSM changes from one state to another based on:

  • Current state
  • Input conditions
  • Clock events

FSMs are commonly used to implement control logic in digital systems.

Examples include:

  • Protocol controllers
  • Bus controllers
  • Traffic light controllers
  • UART controllers
  • Memory controllers
  • SoC control logic

Key Idea

An FSM represents control behavior as a set of states and transitions between those states.

States, Transitions & State Diagrams

Understanding how an FSM represents the behavior of a digital system.

What is a State?

A state represents a particular condition or mode of operation of a digital system. For example, a simple controller might have three states:

  • IDLE — waiting for an operation to begin.
  • ACTIVE — performing the operation.
  • DONE — indicating that the operation has completed.

At any given time, the FSM has one current state.

What is a State Transition?

A state transition is the movement of an FSM from one state to another. The transition normally depends on an input condition and occurs according to the FSM's clocked behavior.

For example: 


IDLE → ACTIVE → DONE

If the required input condition is not satisfied, the FSM may remain in its current state.

Current State and Next State

FSM logic can be divided into two important concepts:

Current State

The state in which the FSM is currently operating.

It is stored using sequential logic such as flip-flops.

Next State

The state that the FSM will enter after the next active clock edge.

It is determined by the current state and input conditions.

Moore vs Mealy FSM

Understanding the two common ways FSM outputs are generated.

Moore Machine

In a Moore FSM, the output depends only on the current state. 


Output = f(Current State)

The output does not directly depend on the input.

Example

Suppose an FSM has these states:

  • IDLE → output = 0
  • ACTIVE → output = 1
  • DONE → output = 0

The output is determined by whichever state the FSM is currently in.

Key Point

Moore output depends only on the current state.

Mealy Machine

In a Mealy FSM, the output depends on both the current state and the input. 


Output = f(Current State, Input)

Therefore, a change in the input can affect the output without necessarily requiring a state change.

Example

Suppose an FSM is in the ACTIVE state. If: 


done = 1

the output could immediately indicate completion according to the combinational output logic.

Key Point

Mealy output depends on the current state and input.

Moore vs Mealy Comparison

Feature Moore Mealy
Output depends on Current state Current state + input
Output equation Output = f(State) Output = f(State, Input)
Input directly affects output? No Yes
Typical output behavior Changes with state Can respond to input changes

FSM Design Structure

Understanding the main building blocks used to implement an FSM in RTL.

Three Main Parts of an FSM

A typical synchronous FSM can be divided into three major parts:

1. State Register

Stores the current state of the FSM.

Implemented using sequential logic and a clock.

2. Next-State Logic

Determines the next state based on the current state and inputs.

Usually implemented using combinational logic.

3. Output Logic

Determines the FSM outputs.

The exact dependency depends on whether the FSM is Moore or Mealy.

Basic FSM Architecture 


                    Inputs
                       │
                       ↓
              ┌─────────────────┐
              │  Next-State     │

                       │

                 Next State

           Next-State    Output Logic
              Logic           │

State Register

The state register stores the current state and updates it on the active clock edge. For example: 

always @(posedge clk) begin

    state <= next_state;

end

This means that the FSM's state changes synchronously with the clock.

Next-State Logic

The next-state logic determines which state should be entered next. For example: 

always @(*) begin

    case (state)

        IDLE:
            if (start)
                next_state = ACTIVE;
            else
                next_state = IDLE;

        ACTIVE:
            if (done)
                next_state = DONE;
            else
                next_state = ACTIVE;

        DONE:
            next_state = IDLE;

        default:
            next_state = IDLE;

    endcase

end

Output Logic

The output logic determines the value of the FSM's outputs. For a simple Moore FSM, the output can be based only on the current state: 

always @(*) begin

    case (state)

        IDLE:
            busy = 1'b0;

        ACTIVE:
            busy = 1'b1;

        DONE:
            busy = 1'b0;

        default:
            busy = 1'b0;

    endcase

end

Important RTL Concept

State register → sequential logic

Next-state logic → combinational logic

Output logic → combinational logic or registered logic depending on the design

FSM State Encoding

Understanding how symbolic FSM states are represented using binary values.

What is State Encoding?

An FSM contains symbolic states such as IDLE, ACTIVE and DONE. Hardware cannot directly store these names. The states must be represented using binary values stored in flip-flops.

For example, a three-state FSM could use:

State Binary Encoding
IDLE 00
ACTIVE 01
DONE 10

Common State Encoding Styles

Several encoding styles can be used when implementing FSMs. The commonly discussed styles are:

  • Binary Encoding
  • One-Hot Encoding
  • Gray Encoding

1. Binary Encoding

Binary encoding uses the minimum number of bits required to represent the states. For N states, approximately log₂(N) bits are required.

For example, four states can be represented using two bits: 


IDLE   = 2'b00
ACTIVE = 2'b01
DONE   = 2'b10
ERROR  = 2'b11

Binary encoding uses fewer flip-flops, but the decoding logic can become more complex depending on the FSM.

2. One-Hot Encoding

In one-hot encoding, each state is represented by a separate bit. Only one bit is normally set to 1 at a time. 


IDLE   = 4'b0001
ACTIVE = 4'b0010
DONE   = 4'b0100
ERROR  = 4'b1000

For four states, four flip-flops are used.

3. Gray Encoding

Gray encoding uses values where adjacent states differ by only one bit. For example: 


00
01
11
10

Gray-style encoding can be useful in designs where reducing the number of changing state bits between transitions is desirable.

Encoding Comparison

Encoding Flip-Flops Main Characteristic
Binary Fewer Compact representation
One-Hot One per state Simple state decoding
Gray Depends on state count Adjacent states differ by one bit

SystemVerilog State Representation

SystemVerilog provides enum, which can make FSM state definitions easier to read and maintain. For example: 

typedef enum logic [1:0] {

    IDLE   = 2'b00,
    ACTIVE = 2'b01,
    DONE   = 2'b10

} state_t;

We will study SystemVerilog enumerations in much greater detail in the dedicated SystemVerilog course. Here, the example is only to show how symbolic state names can be represented.

Interview Tip

Binary encoding uses fewer state bits, while one-hot encoding uses one bit per state. The best encoding depends on the target technology, design requirements and synthesis strategy.

Simple FSM Example

Build a basic three-state controller using Verilog RTL.

Controller Requirements

Let's design a simple controller with three states:

  • IDLE — waiting for a start request.
  • ACTIVE — performing an operation.
  • DONE — operation has completed.

The controller uses two inputs:

  • start — requests the operation to begin.
  • done — indicates that the operation has completed.

State Transition 


             start = 1
        ┌─────────────────┐
        │                 ↓
     ┌──────┐          ┌────────┐
     │ IDLE │          │ ACTIVE │
     └──────┘          └────────┘
        ↑                  │
        │                  │ done = 1
        │                  ↓
        │              ┌────────┐
        └──────────────│  DONE  │
                       └────────┘

The transitions are:

Current State Condition Next State
IDLE start = 0 IDLE
IDLE start = 1 ACTIVE
ACTIVE done = 0 ACTIVE
ACTIVE done = 1 DONE
DONE Any condition IDLE

Verilog Implementation 

module simple_fsm (

    input clk,
    input reset,

    input start,
    input done,

    output reg busy

);

reg [1:0] state;
reg [1:0] next_state;

localparam IDLE   = 2'b00;
localparam ACTIVE = 2'b01;
localparam DONE   = 2'b10;




always @(posedge clk) begin

    if (reset)
        state <= IDLE;
    else
        state <= next_state;

end




always @(*) begin

    next_state = state;

    case (state)

        IDLE: begin

            if (start)
                next_state = ACTIVE;
            else
                next_state = IDLE;

        end

        ACTIVE: begin

            if (done)
                next_state = DONE;
            else
                next_state = ACTIVE;

        end

        DONE: begin

            next_state = IDLE;

        end

        default: begin

            next_state = IDLE;

        end

    endcase

end




always @(*) begin

    case (state)

        IDLE:
            busy = 1'b0;

        ACTIVE:
            busy = 1'b1;

        DONE:
            busy = 1'b0;

        default:
            busy = 1'b0;

    endcase

end

endmodule

Understanding the RTL

  • state stores the current FSM state.
  • next_state determines the state that will be stored at the next clock edge.
  • The first always block implements the state register.
  • The second always block implements next-state logic.
  • The third always block implements the Moore output logic.
  • The reset places the FSM into the known IDLE state.

Why Use Three Blocks?

Separating the FSM into state-register, next-state and output logic makes the RTL easier to understand, debug and maintain. 


Block 1
State Register
     ↓
Current State

Block 2
Next-State Logic
     ↓
Next State

Block 3
Output Logic
     ↓
Output

Important RTL Rule

Use non-blocking assignments for clocked state updates and blocking assignments for combinational next-state and output logic.

FSM State Transition Table

Use a transition table to describe exactly how the FSM behaves for each input condition.

What is a State Transition Table?

A state transition table lists the current state, input conditions and the resulting next state. It provides a systematic way to convert an FSM specification into RTL.

Example: Simple Controller

Current State start done Next State
IDLE 0 X IDLE
IDLE 1 X ACTIVE
ACTIVE X 0 ACTIVE
ACTIVE X 1 DONE
DONE X X IDLE

X means that the particular input does not affect the transition for that row.

From Specification to RTL

A common FSM design process is:

  1. Understand the functional requirement.
  2. Identify all required states.
  3. Determine the conditions for each transition.
  4. Create the state transition table.
  5. Create the state diagram.
  6. Choose an appropriate state encoding.
  7. Implement the state register.
  8. Implement next-state logic.
  9. Implement output logic.
  10. Simulate and verify the FSM.

Design Tip

Before writing RTL, make sure the state diagram and transition conditions are completely defined.

A clear specification makes FSM implementation and debugging much easier.

Mealy FSM Implementation

Implementing an FSM whose output depends on the current state and input.

Mealy FSM Example

Let's modify the previous controller so that the output done_pulse is generated when the FSM is in the ACTIVE state and the done input is asserted. Therefore: 


done_pulse = ACTIVE AND done

Because the output depends on both the current state and the input, this is a Mealy FSM.

Verilog Implementation 

module mealy_fsm (

    input clk,
    input reset,

    input start,
    input done,

    output reg done_pulse

);

reg [1:0] state;
reg [1:0] next_state;

localparam IDLE   = 2'b00;
localparam ACTIVE = 2'b01;

// State Register

always @(posedge clk) begin

    if (reset)
        state <= IDLE;
    else
        state <= next_state;

end

// Next-State Logic

always @(*) begin

    next_state = state;

    case (state)

        IDLE: begin

            if (start)
                next_state = ACTIVE;
            else
                next_state = IDLE;

        end

        ACTIVE: begin

            if (done)
                next_state = IDLE;
            else
                next_state = ACTIVE;

        end

        default: begin

            next_state = IDLE;

        end

    endcase

end

// Output Logic

always @(*) begin

    done_pulse = 1'b0;

    case (state)

        ACTIVE: begin

            if (done)
                done_pulse = 1'b1;

        end

        default: begin

            done_pulse = 1'b0;

        end

    endcase

end

endmodule

Understanding the Output Logic

The output is generated using: 

done_pulse = 1'b0;

if (state == ACTIVE && done)
    done_pulse = 1'b1;

Therefore, the output depends on:

  • Current state = ACTIVE
  • Input done = 1

If either condition is false, the output remains zero.

Moore vs Mealy in This Example

FSM Type Output Depends On Example
Moore Current State busy = (state == ACTIVE)
Mealy Current State + Input done_pulse = (state == ACTIVE) && done

Important Observation

A Mealy output can respond to an input change while the FSM remains in the same state because the input is part of the output logic.

Interview Tip

Moore: Output = function(Current State)

Mealy: Output = function(Current State, Input)

FSM Reset and Default State

Understanding how an FSM starts in a known state and handles unexpected states.

Why Does an FSM Need Reset?

An FSM should normally start from a known state when the system begins operation. A reset signal is commonly used to place the FSM into a defined initial state.

For example, our controller can start in: 


IDLE

Reset in the State Register 

always @(posedge clk) begin

    if (reset)
        state <= IDLE;
    else
        state <= next_state;

end

When reset = 1 at the active clock edge, the FSM moves into the IDLE state.

Why Use a Default Case?

The default branch provides a defined behavior if the FSM state does not match any of the expected states. For example: 

always @(*) begin

    next_state = state;

    case (state)

        IDLE:
            next_state = ACTIVE;

        ACTIVE:
            next_state = DONE;

        DONE:
            next_state = IDLE;

        default:
            next_state = IDLE;

    endcase

end

If the FSM reaches an unexpected state, the default branch directs it back to IDLE.

Reset and Default State Comparison

Feature Reset Default Case
Purpose Initialize the FSM Handle an unexpected state
Typical location State register Next-state/output logic
Example action Set state to IDLE Return next state to IDLE

Reset establishes the initial state, while a default branch provides defined behavior for states that are not explicitly handled.

FSM Design Workflow

A systematic process for converting a functional requirement into FSM RTL.

Step 1 — Understand the Requirement

Start by understanding exactly what the controller needs to do. Identify:

  • Inputs
  • Outputs
  • Operating conditions
  • Required behavior
  • Reset behavior

Step 2 — Identify the States

Break the required behavior into distinct operating conditions. For example: 


IDLE
ACTIVE
DONE

Each state should represent a meaningful condition of the system.

Step 3 — Define Transitions

Determine what condition causes the FSM to move from one state to another. For example: 


IDLE + start → ACTIVE

ACTIVE + done → DONE

DONE → IDLE

Step 4 — Create the State Diagram

Draw the states and connect them using arrows that represent the transition conditions. This provides a visual representation of the controller behavior.

Step 5 — Create the Transition Table

List the current state, input conditions and next state. This helps identify missing conditions and unexpected transitions before writing RTL.

Step 6 — Choose State Encoding

Choose an encoding such as:

  • Binary encoding
  • One-hot encoding
  • Gray encoding

The appropriate choice depends on the design requirements and target implementation.

Step 7 — Implement the State Register 

always @(posedge clk) begin

    if (reset)
        state <= IDLE;
    else
        state <= next_state;

end

Step 8 — Implement Next-State Logic

Use combinational logic to determine the next state. A case statement is commonly used: 

always @(*) begin

    next_state = state;

    case (state)

        IDLE:
            ...

        ACTIVE:
            ...

        DONE:
            ...

        default:
            next_state = IDLE;

    endcase

end

Step 9 — Implement Output Logic

Determine whether the design requires Moore or Mealy output behavior.

  • Moore: output depends on current state.
  • Mealy: output depends on current state and inputs.

Step 10 — Verify the FSM

Finally, simulate the design and verify:

  • Reset behavior
  • Every state transition
  • Every input condition
  • Output behavior
  • Unexpected or invalid conditions
  • Return-to-IDLE behavior
