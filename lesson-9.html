1. What Are Pipeline Hazards?

Understanding why a pipeline sometimes cannot continue normally.

What is a Pipeline Hazard?

A pipeline hazard is a situation that prevents an instruction or data transaction from progressing through the pipeline during the expected clock cycle.

In an ideal pipeline, a new transaction enters the pipeline every clock cycle and each transaction advances one stage at every clock edge. Real designs can introduce dependencies, resource conflicts or control-flow changes that prevent this ideal behavior.

Ideal Pipeline 


Cycle 1:

A → Stage 1


Cycle 2:

A → Stage 2
B → Stage 1


Cycle 3:

A → Stage 3
B → Stage 2
C → Stage 1


Cycle 4:

A → Output
B → Stage 3
C → Stage 2
D → Stage 1

This is the ideal case where every stage can continue operating without interruption.

When Does a Hazard Occur?

A hazard occurs when the next operation cannot safely proceed at the expected time. For example, a later operation may need a value that an earlier operation has not produced yet.

     | Produces Data
     v
Operation B
     |
     | Needs Data
     v
Result

If Operation B reaches the required pipeline stage before the data from Operation A is available, the pipeline needs a mechanism to handle the situation.

1. Data Hazard

A data hazard occurs when one operation depends on a value produced or modified by another operation. 


Instruction A:

R1 = R2 + R3


Instruction B:

R4 = R1 + R5

Instruction B requires the new value of R1 produced by Instruction A. Because both instructions can overlap inside the pipeline, the required value may not yet be available.

2. Structural Hazard

A structural hazard occurs when two pipeline operations require the same hardware resource at the same time.

      v
+-------------+
|   Shared    |
|   Resource  |
+-------------+
      ^
      |
Instruction B

For example, if two pipeline stages require access to a single resource that can serve only one request at a time, one operation may have to wait.

3. Control Hazard

A control hazard occurs when the pipeline does not immediately know which operation should execute next because of a control-flow decision. Branches are a common example. 


             Branch
                |
          +-----+-----+
          |           |
        Path A       Path B

Until the branch decision is resolved, the pipeline may have already started processing operations from the wrong path. Those operations may need to be discarded.

What is a Pipeline Stall?

A stall temporarily prevents part of the pipeline from advancing. The pipeline waits until the condition causing the hazard has been resolved. 


Normal:

Cycle 1 → A
Cycle 2 → B
Cycle 3 → C
Cycle 4 → D


With Stall:

Cycle 1 → A
Cycle 2 → B
Cycle 3 → Stall
Cycle 4 → C
Cycle 5 → D

What is a Bubble?

A bubble is an empty slot introduced into the pipeline. It represents a cycle in which useful work is not progressing through a particular pipeline stage. 


Cycle 1 → A
Cycle 2 → B
Cycle 3 → Bubble
Cycle 4 → C

Stalls and bubbles reduce the ideal throughput of the pipeline, but they can be necessary to maintain correct behavior.

Why Hazard Handling Is Important

A pipeline must always produce the correct result. Performance is important, but correctness comes first. The design therefore needs to detect situations where normal pipeline operation could produce incorrect data or incorrect control flow.

Important Observation

Not every pipeline requires the same hazard-handling mechanisms. The required solution depends on the architecture, pipeline depth, available hardware resources and timing requirements.

Key Idea

Pipeline hazards are conditions that prevent ideal pipeline execution. The three major categories are data hazards, structural hazards and control hazards.

Hazards may require techniques such as forwarding, stalling, bubble insertion, resource management or pipeline flushing.

2. Data Hazards

Understanding hazards caused by dependencies between pipeline operations.

What is a Data Hazard?

A data hazard occurs when one operation depends on data produced or modified by another operation. In a pipelined design, multiple operations overlap in time. This can cause a later operation to reach a stage before the data it requires is available.

Simple Example 


Operation 1:

R1 = R2 + R3


Operation 2:

R4 = R1 + R5

Operation 2 needs the new value of R1 produced by Operation 1. Therefore, Operation 2 depends on Operation 1. 


Operation 1
     |
     | Produces R1
     v
Operation 2
     |
     | Reads R1
     v
Result

Why Does Pipelining Create the Problem?

Without pipelining, Operation 1 could finish before Operation 2 starts. With pipelining, both operations can be active at the same time. 


Cycle 1:

Operation 1 → Stage 1


Cycle 2:

Operation 1 → Stage 2
Operation 2 → Stage 1


Cycle 3:

Operation 1 → Stage 3
Operation 2 → Stage 2

At this point, Operation 2 may need a value that Operation 1 has not yet written back.

Read-After-Write Dependency

The most common data hazard in a simple pipeline is the Read-After-Write (RAW) dependency. It occurs when a later operation tries to read a value before an earlier operation has completed writing that value. 


Instruction A:

R1 = R2 + R3


Instruction B:

R4 = R1 + R5

Instruction A writes R1. Instruction B reads R1. Therefore, Instruction B must receive the correct result from Instruction A.

Pipeline Example

Cycle Instruction A Instruction B
1 Execute —
2 Next Stage Execute
3 Next Stage Next Stage

If Instruction B requires R1 during Cycle 2, but Instruction A does not produce R1 until a later stage, a hazard exists.

How Can We Handle a Data Hazard?

There are two fundamental approaches commonly used in pipelines:

  • Forwarding: Send the required result directly from a later pipeline stage to the stage that needs it.
  • Stalling: Temporarily stop the dependent operation until the required data is available.

Important RTL Perspective

At the RTL level, pipeline registers define when values become available to subsequent stages. For example: 


always @(posedge clk) begin

    stage1 <= a + b;

    stage2 <= stage1 + c;

end

Because these are nonblocking assignments, stage2 receives the previous value of stage1. This clock-cycle separation is fundamental to understanding pipeline data hazards.

Key Idea

A data hazard occurs when overlapping pipeline operations have a data dependency that cannot be satisfied at the required time.

The most important case to understand is the RAW dependency, which can be handled using techniques such as forwarding or stalling.

3. RAW (Read-After-Write) Hazard

Understanding the most common data hazard in a pipelined processor.

What is a RAW Hazard?

RAW stands for Read-After-Write. A RAW hazard occurs when a later instruction needs to read a value that an earlier instruction has not yet written.

Basic Example 


Instruction 1:

R1 = R2 + R3


Instruction 2:

R4 = R1 + R5

Instruction 1 produces the new value of R1. Instruction 2 requires that new value of R1. Therefore, Instruction 2 cannot safely use an old value of R1. 


Instruction 1

     | Writes R1

     | Reads R1
     |

Why Does RAW Become a Hazard?

In a pipelined processor, instructions overlap. The instruction that produces the value may still be somewhere inside the pipeline when the dependent instruction needs to read it.

Cycle 3:

Instruction 1 → Stage 3
Instruction 2 → Stage 2


Cycle 4:

Instruction 1 → Write Result
Instruction 2 → Needs Result

If the result of Instruction 1 is not available to Instruction 2 at the required time, a RAW hazard exists.

Method 1 — Forwarding

One common solution is forwarding, also called bypassing. Instead of waiting for the result to be written back to the register file, the result can be forwarded directly from a pipeline stage to the stage that needs it.

If the required value cannot be forwarded in time, the pipeline can insert a stall.

RAW Hazard in RTL Thinking

At the RTL level, a dependency can appear between registered values. For example:

Because these are nonblocking assignments, result2 uses the previous value of result1. This behavior creates a clock-cycle dependency between the two operations.

A RAW dependency itself is not necessarily a problem. It becomes a RAW hazard when the pipeline timing causes the consumer to require the value before the producer has made it available.

4. Pipeline Stalls and Bubbles

Understand how a pipeline pauses and how bubbles are introduced to maintain correctness.

What is a Pipeline Stall?

A pipeline stall occurs when a pipeline temporarily stops advancing an instruction or transaction because the required condition for safe execution has not yet been satisfied.

A stall is commonly used when a dependent instruction needs data that is not yet available.

Why Do We Need a Stall?

Consider two dependent operations: 


Instruction A:

R1 = R2 + R3


Instruction B:

R4 = R1 + R5

Instruction B needs the new value of R1. If that value is not available when Instruction B reaches the required pipeline stage, allowing it to continue could produce an incorrect result. The pipeline therefore needs to wait. 


Instruction A
     |
     | Produces R1
     v
   R1
     ^
     |
     | Requires R1
     |
Instruction B

        ↓

      STALL

What is a Bubble?

A bubble is an empty slot introduced into the pipeline. It represents a cycle in which a particular pipeline stage does not perform useful work for a new transaction. 


Normal Pipeline:

Cycle 1 → A
Cycle 2 → B
Cycle 3 → C
Cycle 4 → D


With Bubble:

Cycle 1 → A
Cycle 2 → B
Cycle 3 → Bubble
Cycle 4 → C
Cycle 5 → D

The bubble effectively creates additional time for the earlier operation to complete.

Stall vs Bubble

Term Meaning
Stall Temporarily prevents normal pipeline progress.
Bubble An empty pipeline slot created as a result of the stall.

Example Pipeline

Consider a simple three-stage pipeline: 


Stage 1 → Stage 2 → Stage 3

Normally, transactions move through the pipeline as follows: 


Cycle 1:

Cycle 2:

B → Stage 1
A → Stage 2


Cycle 3:

Cycle 2:

Cycle 3:

A → Stage 3

B → Stage 2

Effect of a Stall on Throughput

A stall introduces an empty cycle into the pipeline. Therefore, stalls can reduce the ideal throughput of the design. 


Without Stall:

A → B → C → D → E


With Stall:

A → B → Bubble → C → D → E

The more frequently stalls occur, the further the actual throughput can move away from the ideal throughput.

Pipeline Control During a Stall

Basic RTL Concept

A simplified stall mechanism can be represented by holding a pipeline register when a stall condition is active. 


always @(posedge clk) begin

    if (reset) begin

        stage1 <= 8'b0;

    end

    else if (stall) begin

        stage1 <= stage1;

    end

    else begin

        stage1 <= new_data;

    end

end

In synthesizable RTL, the explicit self-assignment is often unnecessary because omitting the assignment in a clocked block also holds the register. The important concept is that the register retains its previous value when the pipeline is stalled.

Bubble Insertion

A bubble can also be created by preventing valid data from advancing into the next stage. This is commonly handled using a valid signal. 


Data     → Stage 1 → Stage 2

Valid    →    1    →    0

Here, the stage may contain a value, but the valid bit indicates that the value should not be treated as a valid transaction.

Stalls maintain correctness, but they can reduce performance. Therefore, good pipeline architectures try to avoid unnecessary stalls. Techniques such as forwarding can allow dependent operations to continue when the required value is already available.

Important Observation

A stall is not an error. It is a deliberate control action used to prevent incorrect pipeline execution. The design should stall only when necessary and allow normal execution whenever it is safe.

Key Idea

A pipeline stall temporarily prevents normal progress, while a bubble represents the empty slot created in the pipeline.

Stalls may reduce throughput, but they are an important mechanism for maintaining correct operation when a hazard cannot be resolved immediately.

5. Forwarding and Bypassing

Learn how a pipeline can provide a recently generated result directly to a dependent operation without waiting for normal write-back.

What is Forwarding?

Forwarding, also called bypassing, is a technique used to resolve certain data hazards by sending a result directly from one pipeline stage to another stage that needs it.

Instead of waiting for the result to travel through the normal write-back path, the value is taken from an intermediate pipeline stage and forwarded to the dependent operation.

Why Do We Need Forwarding?

Consider two dependent instructions: 


Instruction 1:

R1 = R2 + R3


Instruction 2:

R4 = R1 + R5

Instruction 2 needs the new value of R1 produced by Instruction 1. Without forwarding, Instruction 2 may have to wait until the value is written back to the register file. With forwarding, the result can potentially be sent directly to the stage where Instruction 2 needs it.

7. Structural Hazards

Understanding hazards caused by competing hardware resources.

What is a Structural Hazard?

A structural hazard occurs when two or more pipeline operations require the same hardware resource at the same time, but the resource cannot support all of those requests simultaneously.

Unlike a data hazard, which is caused by a dependency between operations, a structural hazard is caused by a limitation in the available hardware resources.

Simple Example

Suppose a processor has only one memory interface, but two pipeline operations need to access memory during the same clock cycle.

What is a Control Hazard?

A control hazard occurs when the pipeline does not know which instruction or operation should execute next because the next path depends on a control decision.

What is a Pipeline Flush?

A pipeline flush is the process of removing or invalidating operations that should no longer continue through the pipeline. It is commonly required when the pipeline has already started processing instructions that are later determined to be invalid or on the wrong execution path.

Why is a Flush Required?

Consider a branch instruction. Before the branch decision is known, the processor may fetch instructions from one possible path. If the branch is later determined to take another path, those previously fetched instructions must not be allowed to modify the architectural state.

19. Pipeline Efficiency & CPI

Understand latency, throughput, CPI, pipeline efficiency, and the performance impact of stalls and bubbles.

Why Pipeline Performance Matters

A pipeline improves processor performance by allowing multiple instructions or transactions to be processed simultaneously in different stages.

To understand how efficiently a pipeline is operating, we need to understand three important concepts: latency, throughput, and CPI.

1. Pipeline Latency

Latency is the amount of time or number of clock cycles required for one transaction to travel from the beginning of the pipeline to the end.

Consider a simple three-stage pipeline: 


Stage 1 → Stage 2 → Stage 3

A transaction must pass through all three stages before it reaches the output. 


Cycle 1 → Stage 1

Cycle 2 → Stage 2

Cycle 3 → Stage 3

Therefore, the basic pipeline latency is approximately 3 cycles, assuming one cycle per stage.

2. Pipeline Throughput

Throughput describes how frequently completed transactions can be produced.

A major advantage of pipelining is that latency and throughput are different concepts.

A three-stage pipeline may take three cycles for one transaction to travel through the pipeline, but once the pipeline is full, it can potentially complete one transaction every cycle. 


Cycle 1:

Transaction A → Stage 1


Cycle 2:

Transaction B → Stage 1
Transaction A → Stage 2


Cycle 3:

Transaction C → Stage 1
Transaction B → Stage 2
Transaction A → Stage 3


Cycle 4:

Transaction D → Stage 1
Transaction C → Stage 2
Transaction B → Stage 3

After the pipeline is filled, the ideal throughput is: 


1 transaction / cycle

Latency vs Throughput

Concept Meaning
Latency Time required for one transaction to complete.
Throughput Rate at which transactions are completed.

3. CPI — Cycles Per Instruction

CPI stands for Cycles Per Instruction.

It represents the average number of clock cycles required to complete one instruction. 


CPI = Total Clock Cycles / Number of Instructions

For an ideal pipeline, the steady-state CPI can approach: 


CPI = 1

This means the processor can ideally complete one instruction every cycle after the pipeline is filled.

It does not mean that an individual instruction takes only one cycle from start to finish.

CPI Example

Suppose a pipeline processes: 


10 instructions

and requires: 


12 clock cycles

Then: 


CPI = Total Cycles / Instructions

CPI = 12 / 10

CPI = 1.2

20. Pipeline Performance Optimization

Learn how to reduce stalls, bubbles, flushes and structural conflicts to improve pipeline performance.

Why Optimize a Pipeline?

A pipeline can be functionally correct but still perform poorly if it frequently experiences stalls, bubbles, flushes or resource conflicts.

The objective of pipeline optimization is to maintain correctness while minimizing unnecessary delays and maximizing useful work performed per clock cycle. 


Ideal:

A → B → C → D → E


With frequent stalls:

A → B → Stall → C → Stall → D → E

Every unnecessary stall adds execution cycles and can increase the effective CPI.

1. Forwarding

Forwarding is one of the most important techniques for reducing data-hazard stalls.

Without forwarding, a dependent instruction may need to wait until the producer writes its result back. 


Producer
   ↓
Write Back
   ↓
Register File
   ↓
Consumer

With forwarding, an available result can be sent directly to the dependent operation. 


Producer
   ↓
Result
   └────────────→ Consumer

Forwarding can reduce stalls and improve throughput. However, it requires additional datapaths, multiplexers and control logic.

2. Branch Prediction

Branches can create control hazards because the processor may not immediately know which instruction should be fetched next.

Without prediction, the pipeline may have to wait for the branch decision. 


Branch
  ↓
Wait
  ↓
Decision
  ↓

21. Pipeline Design Trade-offs

Understand the trade-offs between pipeline depth, frequency, latency, area, power, complexity and performance.

Why Are Pipeline Trade-offs Important?

Increasing the number of pipeline stages can improve the maximum operating frequency, but it can also increase latency, control complexity, power consumption and the penalty associated with pipeline flushes.

Therefore, pipeline design is not simply about making the pipeline deeper.

The designer must find a suitable balance between frequency, latency, throughput, area, power and complexity. 


                    Pipeline Design
                          |
        +-----------------+-----------------+
        |        |        |        |        |
        v        v        v        v        v
    Frequency Latency    Area    Power  Complexity

1. Pipeline Depth

Pipeline depth refers to the number of stages through which an instruction or transaction passes. 


Shallow Pipeline:

Stage 1 → Stage 2 → Stage 3


Deeper Pipeline:

Stage 1 → Stage 2 → Stage 3 → Stage 4
        → Stage 5 → Stage 6 → Stage 7

A deeper pipeline divides the work into smaller pieces. This can potentially allow a shorter clock period.

2. Pipeline Depth vs Clock Frequency

Consider a workload that requires approximately 9 ns of combinational work.

With three balanced stages: 


9 ns / 3 stages = 3 ns per stage

With six balanced stages: 


9 ns / 6 stages = 1.5 ns per stage

Ignoring register and implementation overhead for this simplified example, the deeper pipeline can potentially operate at a higher frequency.

3. Deeper Pipeline and Latency

Although deeper pipelining can improve clock frequency, an individual transaction may have to pass through more stages. 


3-stage pipeline:

Input → S1 → S2 → S3 → Output


6-stage pipeline:

Input → S1 → S2 → S3 → S4 → S5 → S6 → Output

Therefore, deeper pipelines can increase the number of cycles of latency.

This illustrates an important distinction: 


Higher Frequency
       ≠
Lower Latency

4. Throughput

Once a pipeline is full, a well-designed pipeline can potentially complete one transaction per cycle.

Increasing the depth can therefore help achieve a higher operating frequency and potentially increase throughput.

       ↓
Potentially Higher Throughput

However, this benefit can be reduced by additional stalls, flushes and control overhead.

Shallow Pipeline
      ↓

Deep Pipeline
      ↓
Larger potential flush window

More pipeline stages can increase the number of possible locations from which a result may need to be forwarded.

             | Consumer |

                ↑ ↑ ↑
                | | |
             Forwarding
              Sources

This can increase:

  • Multiplexer complexity
  • Comparison logic
  • Control logic
  • Verification effort
  • Timing complexity

7. Area Trade-off

Additional pipeline stages require additional pipeline registers and associated control and data paths. 


More Pipeline Stages
        ↓
More Pipeline Registers
        ↓
Potentially More Area

Additional forwarding paths and duplicated resources can further increase hardware area.

8. Power Trade-off

Pipeline registers and control logic switch every cycle when active.

Increasing the amount of hardware can therefore affect dynamic power. 


More Registers
      +
More Control Logic
      +
More Switching
      ↓
Potentially Higher Dynamic Power

Clock distribution to a larger number of sequential elements can also contribute to power and implementation complexity.

Pipeline stages must satisfy setup and hold requirements, and the clock period must account for the combinational delay and sequential overhead.

≈

Combinational Delay
+

Simply dividing logic into more stages does not guarantee unlimited frequency improvement because pipeline registers themselves introduce overhead.

22. Pipeline Hazards Review

What Is a Pipeline Hazard?

A pipeline hazard is a condition that prevents an instruction or transaction from proceeding normally through the pipeline.

The three major categories of pipeline hazards are: 


Pipeline Hazards
      |
      +---- Data Hazard
      |
      +---- Control Hazard
      |
      +---- Structural Hazard

1. Data Hazard

A data hazard occurs when an instruction depends on data produced by another instruction that has not yet completed. 


Instruction 1:

R1 = R2 + R3


Instruction 2:

R4 = R1 + R5

Instruction 2 requires the value of R1 produced by Instruction 1.

Common techniques for handling data hazards include:

  • Forwarding
  • Stalling
  • Bubble insertion

2. Forwarding

Forwarding allows a result to be sent directly from a pipeline stage to a dependent operation without waiting for the normal register write-back path. 


Producer
   |
   | Result
   v
Forwarding Path
   |
   v
Consumer

Forwarding can reduce unnecessary stalls and improve pipeline throughput.

3. Stalling

If a dependency cannot be safely resolved by forwarding, the pipeline may need to stop temporarily. 


Normal:

A → B → C → D


With Stall:

A → B → STALL → C → D

A stall adds one or more cycles to the execution time.

4. Bubble Insertion

A bubble represents an empty or invalid pipeline slot inserted to safely separate dependent operations. 


Instruction A
      ↓
Instruction B
      ↓
   Bubble
      ↓
Instruction C

Bubbles help maintain correctness but can reduce performance.

5. Control Hazard

A control hazard occurs when the next instruction depends on a control-flow decision such as a branch. 


Branch
  ↓
Which instruction executes next?
  ↓
Branch Decision

Until the branch direction or target is known, the pipeline may not know which instructions should continue.

6. Branch Prediction

Branch prediction attempts to predict the direction or target of a branch so that instruction fetching can continue without waiting for the final decision.

  ↓
Correct?

 |       |

         |

A correct prediction helps maintain pipeline flow. A misprediction requires recovery.

7. Pipeline Flush

A pipeline flush removes instructions that should no longer continue through the pipeline. 


Wrong Path
    ↓
Branch Resolution
    ↓
Misprediction
    ↓
Flush
    ↓
Correct Path

Flushing ensures that incorrect-path instructions do not produce incorrect architectural results.

8. Structural Hazard

A structural hazard occurs when multiple pipeline operations require the same hardware resource at the same time. 


Request A ──┐
            |
            +──→ Shared Hardware Resource
            |
Request B ──┘

Possible solutions include:

  • Duplicate the resource
  • Reschedule the operation
  • Stall one operation

25. Multiple Data Hazards

Understand how multiple dependencies can exist at the same time and how forwarding and stalls must handle them correctly.

What Are Multiple Data Hazards?

A pipeline may contain several instructions that have dependencies on results produced by earlier instructions. These dependencies can occur simultaneously or across consecutive instructions. 


I1 → Produces R1
       ↓
I2 → Uses R1 and Produces R2
       ↓
I3 → Uses R2 and Produces R3
       ↓
I4 → Uses R3

This creates a chain of data dependencies that must be handled correctly by the pipeline.

1. Consecutive RAW Dependencies

Consider three consecutive instructions: 


I1: R1 = R2 + R3

I2: R4 = R1 + R5

I3: R6 = R4 + R7

Here, I2 depends on I1 and I3 depends on I2. 


I1
 ↓
R1
 ↓
I2
 ↓
R4
 ↓
I3

The forwarding logic must correctly handle each dependency as the instructions move through the pipeline.

2. Multiple Dependencies in One Instruction

A single instruction can depend on two different previously generated values. 


I1: R1 = R2 + R3

I2: R4 = R5 + R6

I3: R7 = R1 + R4

I3 requires both R1 and R4. 


R1 ─────→ Operand A
           \
            I3
           /
R4 ─────→ Operand B

Therefore, the forwarding unit may need to select a different forwarding source for each operand.

3. Independent Forwarding for RS1 and RS2

The forwarding decisions for the two source operands are independent. 


RS1 → Forwarding Unit → Forward A

RS2 → Forwarding Unit → Forward B

For example: 


forward_a = EX/MEM

forward_b = MEM/WB

This means operand A receives a result from one pipeline stage while operand B receives a result from another.

4. Multiple Producers

Multiple in-flight instructions may write the same destination register. 


I1: R1 = ...

I2: R1 = ...

I3: Uses R1

The forwarding logic must select the newest valid result. 


Newest Result
     ↓
Highest Priority


Older Result
     ↓
Lower Priority

Selecting an older value can cause functional corruption even though the pipeline appears to be operating normally.

5. Dependency Chain 


I1: R1 = R2 + R3
       ↓
I2: R4 = R1 + R5
       ↓
I3: R6 = R4 + R7
       ↓
I4: R8 = R6 + R9

This is a dependency chain. Each instruction depends on the result of the previous instruction.

Forwarding can allow the chain to progress without unnecessarily waiting for every result to reach the register file.

6. Multiple Hazards With a Load

A dependency chain can also contain a load-use hazard. 


I1: LOAD R1, [ADDR]

I2: ADD R4, R1, R5

I3: ADD R6, R4, R7

I2 may require a stall because of the load-use dependency, while I3 may require forwarding from I2. 


LOAD
 ↓
STALL
 ↓
I2
 ↓
Forward
 ↓
I3

Multiple hazards can increase the number of stall cycles and reduce effective pipeline performance.

9. Design Verification Perspective

Multiple-hazard scenarios are important corner cases for Design Verification.

  • Two operands requiring forwarding
  • Different forwarding sources for RS1 and RS2
  • Consecutive RAW dependencies
  • Multiple instructions writing the same register
  • Load-use followed by another dependency
  • Back-to-back dependent instructions
  • Dependency on register zero
  • Stall followed by forwarding
  • Pipeline recovery after multiple hazards
  • No lost or duplicated transactions
